# Research: SPEC-ORDER-001 — 주문 도메인 착수 전 저장소 조사

이 문서는 **주문/체크아웃에 대한 선례가 전혀 없는 저장소**에서 이 SPEC의 범위를 정하기 위해 실제로 실행한 조사와 그 결과다. 각 결론에는 그것을 뒷받침한 명령 또는 인용 위치를 함께 적는다 — 추정으로 좁힌 범위와 확인으로 좁힌 범위를 구분하기 위해서다.

## §1. 주문 선례 부재 확인 (관측된 사실)

| 확인 항목 | 수단 | 결과 |
|---|---|---|
| `Order` 계열 Prisma 모델 | `prisma/schema.prisma` 전문 읽기 | **부재**. 모델은 `User`, `OAuthAccount`, `RefreshToken`, `Category`, `Product`, `Cart`, `CartItem` 7개뿐 |
| 마이그레이션 이력 | `ls prisma/migrations` | 4건(`init`, `add_catalog_models`, `add_product_name_trgm_index`, `add_cart_cart_item`) — 주문 관련 없음 |
| `features/checkout` / `features/orders` | `find src -type f` | **부재**. `features/`에는 `cart`, `catalog` 두 도메인만 존재 |
| 주문/체크아웃 API 라우트 | `find src/app/api -type f` | **부재**. `auth`, `cart`, `products` 세 그룹만 존재 |
| 결제 의존성 | `package.json` dependencies | **부재**. PG SDK·결제 라이브러리 없음(`@prisma/client`, `bcrypt`, `google-auth-library`, `jose`, `next`, `react`) |
| 결제 환경변수 | `.env.example` | **부재**. `tech.md`가 권고한 `PG_API_KEY`/`PG_SECRET_KEY`/`PG_WEBHOOK_SECRET` 어느 것도 등록되어 있지 않음 |
| 코드 내 결제/주문 언급 | `src`·`prisma` 전체 grep(`order\|checkout\|payment\|결제\|주문`) | 실질 매치 2건뿐이며 둘 다 **미래 시제의 위임 주석**: `cart.ts:11` "checkout owns its own price confirmation", `cart-service.ts:204` "no stock is reserved or decremented (REQ-CART-015); checkout owns that" |

결론: 이 SPEC은 주문 도메인의 **첫 SPEC**이며, 참고할 기존 구현이 없다. 반면 장바구니 쪽에서 **명시적으로 위임된 두 책임**이 코드 주석 수준까지 남아 있어, 이 SPEC의 최소 책임 범위는 추정이 아니라 인용으로 확정된다.

## §2. 조사 질문 1 — 결제(PG) 처리가 이 SPEC의 범위인가

### 확인된 근거

1. `tech.md` §결제(PG) 연동 방식 — **"PG사 선택: 특정 PG사는 이번 문서에서 확정하지 않음"**. 후보로 토스페이먼츠/KG이니시스/Stripe를 나열만 하고, "실제 선택은 사업 요구사항(정산 방식, 수수료, 지원 결제수단)에 따라 별도 결정이 필요하다"고 명시.
2. `product.md` §로드맵 후보 — **#1 "결제(PG) 연동 SPEC"** 이 이미 별도 SPEC 후보로 등재되어 있고, "중복 결제 방지(멱등키), 웹훅 기반 상태 확정, 결제 감사 로그" 를 그 SPEC의 내용으로 지목.
3. `.env.example`에 PG 관련 변수가 하나도 없고 `package.json`에 결제 의존성이 없음(§1).
4. `tech.md`가 요구하는 정합성 전략 중 이 SPEC이 **지금 이행할 수 있는 것**은 멱등키 하나뿐이다 — 나머지(웹훅을 최종 상태 소스로 삼기, 결제 상태 감사 로그)는 PG가 정해져야 성립한다.

### 결론

**결제 처리는 이 SPEC의 범위 밖이다.** 이 SPEC은 주문 기록을 만드는 것까지만 담당하고, 주문은 `pending_payment` 상태로 생성된다. 확정되지 않은 외부 시스템의 인터페이스를 발명하는 것은 `verification-claim-integrity` 관점에서도 근거 없는 설계이며, 나중에 실제 PG가 정해지면 거의 전부 재작성된다.

### 검토했지만 택하지 않은 대안

| 대안 | 내용 | 기각 사유 |
|---|---|---|
| A. 결제까지 이 SPEC에 포함 | PG 어댑터 인터페이스를 추상화해 함께 설계 | PG가 미확정이므로 추상화의 근거가 없다. 실제 PG의 요구(리다이렉트 기반인지 SDK 기반인지, 승인 시점이 언제인지)에 따라 인터페이스가 달라지며, 지금 정한 추상화는 검증할 방법이 없는 추측이다 |
| B. Mock PG로 결제 흐름까지 구현 | 가짜 결제 어댑터로 전체 플로우 완성 | 테스트에서 초록불이 켜지지만 그 초록불이 아무 것도 보증하지 않는다. `product.md`의 최우선 제약이 "결제 데이터 정합성"인데, 가짜 어댑터에 대한 정합성 검증은 정합성 증거가 아니다 |
| C. 이 SPEC 자체를 결제 확정까지 보류 | 주문 SPEC을 결제 SPEC 뒤로 미룸 | 주문 기록 없이 결제만 설계할 수는 없다. 순서상 주문 도메인이 먼저다. 또한 SPEC-CART-001이 이미 재고·가격 책임을 체크아웃으로 위임해 둔 상태여서, 이 SPEC이 없으면 그 두 구멍이 계속 열려 있다 |

**확정된 부분**(plan.md §0 #1, 사용자 확인 2026-08-31): "주문 먼저 생성 후 결제" 순서를 채택한다. `pending_payment → paid` 전이의 소유자는 후속 결제 SPEC이며, 이 SPEC은 전이 로직을 만들지 않는다. 반대 순서("결제 승인 후 주문 생성")는 기각되었다. 그럼에도 주문 모델 자체는 순서가 바뀌어도 재사용 가능하도록 상태 필드만 두는 형태를 유지한다.

## §3. 조사 질문 2 — "주문 생성 트랜잭션"이 구체적으로 무엇을 해야 하는가

네 가지 후보 동작(a)~(d)을 각각 "기계적으로 필요한가"로 판정했다.

### (a) 장바구니 항목의 재고 유효성 재확인 — **필요**

`cart-service.ts`의 재고 검사는 담기/수량변경 **요청 시점**의 읽기 전용 검사이며(`addItem`의 `alreadyHeld + quantity > product.stock` 분기), 아무 것도 잡아두지 않는다. `guest_cart_id` 쿠키 수명이 14일이므로 장바구니 항목은 최대 2주 전의 재고 판단에 근거한다. 따라서 주문 시점 재확인은 선택이 아니라 필수다.

### (b) 주문 시점 가격 스냅샷 — **필요**

`prisma/schema.prisma`의 `CartItem`에는 **가격 컬럼이 아예 없고**, `cart-repository.ts`가 매 조회마다 `Product.price`를 조인한다. `cart.ts` 주석이 이 설계를 명시적으로 설명하며 "checkout owns its own price confirmation"이라고 후속 소유자를 지목한다. 즉 주문 항목이 단가를 보존하지 않으면, 상품 가격이 바뀌는 순간 과거 주문의 금액이 소급해서 바뀐다 — 회계상 성립하지 않는다.

가격 스냅샷만으로는 부족한 부분이 하나 더 있다: **주문서를 그린 시점과 제출 시점 사이에 가격이 바뀌는 창**. 이 SPEC은 클라이언트가 확인한 금액을 함께 제출하게 하고 서버 재계산값과 다르면 거부하는 방식으로 닫는다(REQ-ORDER-014). 대안은 design.md §4에 정리.

### (c) 재고 차감 — **필요, 그리고 이 SPEC의 책임임이 인용으로 확정됨**

REQ-CART-015 원문: "실제 재고 확정/차감은 향후 체크아웃 SPEC의 책임이다". 추정이 아니라 선행 SPEC이 명시적으로 넘긴 책임이다.

차감 **시점**은 두 갈래가 가능하다.

| 시점 | 장점 | 단점 |
|---|---|---|
| 주문 생성 시(이 SPEC의 결정) | 주문 기록과 재고가 같은 트랜잭션 안에 있어 초과 판매가 구조적으로 막힌다. 결제 SPEC이 없는 지금 시점에도 완결적으로 검증 가능하다 | 결제하지 않고 방치된 주문이 재고를 잡아둔다 → 해제 정책이 필요해진다(plan.md §0 #2, 이 SPEC 범위 밖으로 잠정 결정) |
| 결제 승인 시 | 방치된 주문이 재고를 잡지 않는다 | 결제 SPEC이 존재해야 성립한다. 결제 승인 후 재고가 모자란 상황(승인은 났는데 물건이 없음)이 발생하며, 이는 환불 처리를 수반하는 더 나쁜 실패 형태다 |

`product.md`의 최우선 제약이 "결제 데이터 정합성"이므로 **결제가 성사됐는데 물건이 없는 상태를 만들지 않는 쪽**을 택한다.

### (d) 주문 후 장바구니 비우기 — **필요**

비우지 않으면 주문 완료 직후에도 장바구니에 같은 상품이 남아 있어, 재고는 이미 차감된 상태에서 같은 주문을 다시 제출할 수 있다. 또한 게스트의 경우 `guest_cart_id` 쿠키가 14일간 유지되므로 잔여 장바구니가 오래 남는다. 비우기가 트랜잭션 안에 있어야 하는 이유는 design.md §2.

### 결론

(a)(b)(c)(d) 네 가지 전부 필요하며, 넷은 **하나의 트랜잭션 경계 안에 있어야 한다**(REQ-ORDER-011/012). 근거: 넷 중 어느 하나만 실패해 부분 반영되면 그 결과가 전부 "정합성이 깨진 상태"다 — 주문 없이 줄어든 재고, 재고 차감 없이 생성된 주문, 비워지지 않은 채 주문된 장바구니.

## §4. 조사 질문 3 — "주문서 작성"이 어떤 UI 표면인가

카드 제목("주문서 작성")만으로는 **배송 정보 입력 양식**인지 **주문 확인/검토 단계**인지 갈린다. 문서 증거로 판정했다.

### 확인된 근거

1. `tech.md` §개인정보 최소 수집 원칙 반영 — **"게스트 체크아웃 시 결제/배송에 필요한 최소 정보(이름, 연락처, 배송지)만 수집하고"**. 즉 체크아웃 단계에서 **수집 행위가 일어난다**고 이미 규정되어 있고, 수집 항목까지 열거되어 있다.
2. `product.md` §핵심 기능 #4 — "주문 및 배송 상태 조회". 배송 상태가 존재하려면 배송지가 주문에 기록되어야 한다.
3. `structure.md` 제안 구조 — `app/(shop)/checkout/page.tsx`(체크아웃, 회원/게스트 공통)와 `checkout/guest/page.tsx`(게스트 전용 플로우)를 별도로 제안. 최소한 입력 화면이 전제되어 있다.
4. `User` 모델(`schema.prisma`)에는 이름·연락처·주소 필드가 **없다**. 즉 회원이라도 배송지를 어딘가에서 입력받아야 하며, 저장된 배송지를 재사용하는 경로는 존재하지 않는다.

### 결론

**배송 정보 입력 양식 + 주문 요약 확인이 한 화면에 있는 형태**로 확정한다. 이는 추정이 아니라 `tech.md`가 수집 항목까지 열거한 데 따른 것이며, 열린 질문으로 남기지 않는다.

수집 항목은 `tech.md`의 "이름, 연락처, 배송지"에 우편번호/상세주소 분리와 선택 입력 배송 요청사항을 더한 5개로 확정한다(REQ-ORDER-008). 개인정보 최소 수집 원칙에 따라 그 이상은 받지 않으며, 특히 **이메일은 받지 않는다** — 저장 목적이 현재 SPEC 범위 안에 없기 때문이다(plan.md §0 #4의 잠정 결정, 재검토 가능).

### 남은 UI 관련 관측 사실 (범위 결정에 영향)

- 저장소에 **장바구니 화면이 존재하지 않는다**(`find src/app -name "*.tsx"` 결과에 `cart` 없음). SPEC-STOREFRONT-001 §3이 장바구니 UI와 담기 버튼을 명시적으로 제외했고 후속 SPEC이 아직 없다.
- 따라서 주문서 화면으로 이어지는 **화면상 링크가 존재하지 않는다**. 이 SPEC은 링크를 만들지 않고(진입 동선은 장바구니 UI SPEC의 몫), 주소 직접 진입으로 검증한다. 이 구멍은 숨기지 않고 spec.md §3과 plan.md에 명시한다.

> **위 §4의 결론은 게스트 방문자에 대해서만 유효하다.** 같은 화면을 회원이 열 수 있는가는 별개의 질문이며, 조사 결과 **불가능**으로 판명되었다 — §6.

## §5. 검증 하네스의 한계 (정직하게 기록)

`vitest.config.ts`와 `tests/integration/cart/guest-merge.test.ts`를 읽어 확인한 사실:

- 테스트 환경은 `node`이며, 컴포넌트 테스트만 파일 단위로 `jsdom`을 opt-in한다.
- **살아 있는 PostgreSQL이 없다.** 기존 "통합" 테스트조차 Prisma 클라이언트를 인메모리 fake로 대체한다. `guest-merge.test.ts` 주석이 이를 자인한다 — "with no live PostgreSQL there is no evidence about real constraint enforcement, cascade behaviour, or the concurrent-add race".

이 SPEC의 핵심 주장이 **트랜잭션 원자성**이므로 이 한계는 치명적으로 중요하다. 이 하네스로 관측 가능한 것과 불가능한 것을 acceptance.md §0에서 분류하고, 관측 불가능한 항목은 "실 DB 필요 — 이 SPEC의 자동 Definition of Done에 포함하지 않음"으로 명시한다. 초록불을 원자성의 증거로 제시하지 않는다.

## §6. 조사 질문 4 — 서버 렌더 체크아웃 화면이 회원을 식별할 수 있는가

이 질문은 처음 조사 때 던지지 않았다. plan-audit iteration 2가 제기했고, 그 답이 이 SPEC의 범위를 바꾸었으므로 근거를 여기에 남긴다. **답은 "할 수 없다"이며, 이는 추정이 아니라 저장소에서 직접 확인한 사실들의 귀결이다.**

### 확인된 사실

| # | 확인 항목 | 수단 | 결과 |
|---|---|---|---|
| 1 | 액세스 토큰의 보관 위치 | `src/middleware.ts:18-31` 주석 원문 | REQ-AUTH-009는 토큰을 **클라이언트 메모리에만** 둔다 — "never a cookie, never localStorage/sessionStorage". 같은 주석이 귀결까지 적어 두었다: 클라이언트 JS의 fetch/XHR은 `Authorization: Bearer` 헤더를 붙일 수 있지만 **"a raw top-level browser NAVIGATION ... cannot: a top-level navigation carries no custom request headers"** |
| 2 | 클라이언트 측 토큰 보관소의 실재 | `src/` 전체 grep(`localStorage\|sessionStorage\|AuthContext`) | 매치 **1건**, 그것도 위 (1)의 주석 자체다. 토큰을 담아 두는 스토어·프로바이더가 **존재하지 않는다** |
| 3 | 로그인 후 게스트 쿠키의 운명 | `src/app/api/auth/login/route.ts` 게스트 병합 블록 | 게스트 쿠키가 있으면 병합 후 `buildExpiredGuestCartCookie()`로 **무조건 만료**시킨다. 주석이 무조건인 이유까지 밝힌다("Expired unconditionally, INCLUDING after a failed merge") |
| 4 | 토큰 전달용 우회 쿠키의 선례 | `src/lib/auth/google-oauth.ts` | 리다이렉트가 토큰을 나를 수 없어 `oauth_access_token_handoff`라는 60초짜리 `httpOnly: false` 쿠키를 별도 도입한 전례가 있다. 즉 이 저장소는 이미 같은 벽에 부딪혀 특수 우회로를 만든 적이 있다 |
| 5 | 액세스 토큰의 반환 형태 | `login/route.ts`의 `NextResponse.json({ accessToken })` | 토큰은 JSON 본문으로만 나가며 쿠키로 설정되지 않는다 |

### 결론

(1)+(2)로 **최상위 내비게이션으로 도달하는 서버 렌더 페이지에는 `Authorization` 헤더가 원리적으로 도착하지 않는다.** (3)으로 **로그인한 회원에게는 게스트 쿠키도 없다.** 둘을 합치면 `/checkout`을 여는 회원의 요청은 서버가 볼 수 있는 신원 재료를 **하나도 갖고 있지 않다.** `/checkout/complete/[orderId]`도 같다.

따라서 이 SPEC이 서버 렌더 방식을 유지하는 한(REQ-ORDER-005), 회원 체크아웃은 **구현 방법이 없다.** 해결하려면 SPEC-AUTH-001의 REQ-AUTH-009 전송 결정을 다시 열거나 REQ-ORDER-005를 뒤집어야 하며, 둘 다 이 SPEC 혼자 정할 수 있는 사안이 아니다.

**범위 결정(사용자 확인, 2026-08-31)**: 회원 체크아웃을 이 SPEC의 범위에서 제외하고 게스트 체크아웃만 만든다. 전문은 spec.md §3의 첫 항목, 결정 기록은 plan.md §0 #5.

### 검토했지만 택하지 않은 대안

| 대안 | 내용 | 기각 사유 |
|---|---|---|
| A. 서버가 읽을 수 있는 세션 쿠키를 이 SPEC에서 도입 | `refresh_token`을 서버에서 읽거나, 짧은 수명의 액세스 토큰 핸드오프 쿠키를 추가 | SPEC-AUTH-001의 REQ-AUTH-009가 내린 **보안 결정을 이 SPEC이 조용히 뒤집는 일**이다. (4)의 `oauth_access_token_handoff` 선례가 보여 주듯 그런 쿠키는 수명·`httpOnly` 여부·노출 범위를 따로 논증해야 하는 설계 항목이며, 교차 SPEC 조정 없이 예외로 처리할 수 없다 |
| B. 신원 해석을 클라이언트로 옮김 | `CheckoutForm`이 `Authorization` 헤더를 붙여 장바구니를 가져오게 함 | REQ-ORDER-005(최초 렌더에 브라우저 측 데이터 요청 없음)와 AC-ORDER-005(b)를 정면으로 뒤집는다. 그 요구사항 자체를 재설계해야 하므로 회원 체크아웃 SPEC의 몫이다 |
| C. 회원 요청을 게스트로 강등해 주문 | 토큰을 무시하고 게스트 쿠키로만 처리 | (3)에 의해 회원에게는 게스트 쿠키가 없어 성립하지 않는다. 억지로 새 게스트 id를 발급하면 회원의 장바구니와 무관한 빈 카트를 보게 되며, 만들어진 주문은 그 회원이 다시 열 수도 없다 |
