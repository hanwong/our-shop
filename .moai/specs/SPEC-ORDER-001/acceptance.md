# Acceptance Criteria: SPEC-ORDER-001 — 게스트 주문서 작성 및 주문 생성 트랜잭션

Tier L — AC 상한 25개 이내(**현재 21개**). 각 항목은 REQ-ORDER-XXX 하나 이상을 검증하며, 통과/실패가 이분법으로 판정 가능해야 한다.

> **번호에 `009`와 `017`이 없는 것은 누락이 아니다.** REQ-ORDER-009는 AC-008에, REQ-ORDER-017은 AC-003에 흡수되어 별도 AC를 두지 않았다 — 근거와 매핑은 §1.5. 따라서 실제 AC는 `001~008`, `010~016`, `018~023`의 21개다.

> **범위 전제**: 이 SPEC은 **게스트 체크아웃만** 만든다(spec.md §3 첫 항목). 따라서 아래 시나리오의 "방문자"는 전부 게스트이며, 회원이 등장하는 유일한 AC는 **회원 요청이 거부되는지**를 확인하는 AC-ORDER-022다. 회원이 정상적으로 주문하는 시나리오는 이 SPEC에 존재하지 않는다.

## §0. 검증 수단의 경계 (읽기 전에)

이 SPEC의 핵심 주장은 **트랜잭션 원자성**인데, 이 저장소에는 **살아 있는 PostgreSQL이 없다**(research.md §5). 기존 "통합" 테스트조차 Prisma 클라이언트를 인메모리 fake로 대체하며, `tests/integration/cart/guest-merge.test.ts`가 그 한계를 스스로 밝히고 있다. 따라서 아래 AC는 이 하네스로 **실제 관측 가능한 것만** Then 절에 담고, 나머지는 분류해 명시한다.

| 분류 | 의미 | 해당 항목 |
|---|---|---|
| **하네스 관측 가능** | vitest(node/jsdom) + 인메모리 fake + 정적 소스 검사로 판정 | 대부분의 AC |
| **실 DB 필요 — 자동 DoD 제외** | 살아 있는 PostgreSQL에서만 관측 가능. 이 SPEC의 자동 Definition of Done의 PASS 조건에 **포함하지 않는다** | 아래 이름 붙은 제외 항목 3건 |

### 이름 붙은 제외 항목 (자동 DoD에서 빠지는 것들)

이전 판에서는 이 세 항목을 "AC-012 (c), AC-013 (c), AC-016 (c)"처럼 **Then 절 하위 글자로** 지칭했으나, 그 표기는 해석되지 않는다 — AC-013에는 `(c)`가 없고, AC-012·AC-016의 `(c)`는 제외 사유가 실제로 겨냥하는 대상이 아니다. 아래처럼 **고유 이름**을 부여하고, 각 제외가 그 AC의 어느 Then 하위 항목을 조건 짓는지 명시한다.

| 제외 ID | 소속 AC | 관측 불가능한 것 | 이 AC의 어느 Then을 조건 짓는가 |
|---|---|---|---|
| `AC-012-EXCL-ROLLBACK` | AC-ORDER-012 | PostgreSQL이 실제로 트랜잭션을 되돌리는지 | **(a)·(b)·(c) 전부.** 셋 다 "fake가 롤백을 구현했다"는 같은 전제 위에 서 있다 — 어느 하나만 조건부인 것이 아니다 |
| `AC-013-EXCL-CONCURRENCY` | AC-ORDER-013 | 동시 주문 두 건이 행 잠금으로 직렬화되어 한 건만 성공하는 것 | **없음(별도 주장).** AC-013의 Then (a)·(b)는 순차 단일 요청만으로 전부 관측된다. 이 제외는 Then 하위 항목이 아니라 design.md §3이 주장하는 **별개의 동시성 성질**을 가리킨다 |
| `AC-016-EXCL-UNIQUE-RACE` | AC-ORDER-016 | 동시 도착 두 요청이 `@unique` 위반으로 직렬화되는 2차 방어(design.md §5) | **없음(별도 주장).** AC-016의 Then (a)·(b)·(c)는 순차 재제출(1차 방어)로 전부 관측된다. 이 제외 역시 별개의 동시성 성질이다 |

각 AC 아래 `검증 수단:` 줄로 무엇이 판정하는지 밝힌다. **fake가 흉내 낸 롤백은 PostgreSQL 롤백의 증거가 아니다** — fake로 확인하는 것은 "서비스 코드가 실패 시 롤백 경로로 진입한다"이지 "데이터베이스가 되돌린다"가 아니다.

**그리고 fake가 롤백을 구현하지 않았다면 그 위에 선 AC는 PASS가 아니다.** plan.md §5가 기록한 거짓 초록 위험이 그것이다. AC-ORDER-011·012는 fake DB의 상태 단언에 의존하므로, run-phase는 fake의 롤백 구현 여부를 먼저 확인하고 미구현이면 두 AC를 **PASS로 계상하지 않는다**(각 AC의 `전제:` 줄).

## §1. Given-When-Then 시나리오

### 데이터 모델 및 스냅샷

**AC-ORDER-001** — 주문이 정확히 하나의 게스트 신원에 귀속된다 (REQ-ORDER-001)
- Given: 게스트 쿠키 `G1`을 가진 요청으로 주문을 생성한다
- When: 생성된 `Order` 레코드와 Prisma 스키마를 함께 검사한다
- Then: (a) 주문의 `guestId`가 `G1`과 같다. (b) `Order` 모델에 `userId`·`user` 관계·`@@index([userId])`가 **존재하지 않으며**, `guestId`가 nullable이 아니다. (c) `User` 모델의 diff가 0줄이다.
- 검증 수단: fake DB에 기록된 행 검사 + `prisma/schema.prisma` 정적 검사 + git diff.

**AC-ORDER-002** — 단가·상품명이 주문 시점 값으로 고정된다 (REQ-ORDER-002)
- Given: 가격 `10000`, 이름 `"Tee"`인 상품이 장바구니에 수량 2로 담겨 있다
- When: 주문을 생성한 뒤 상품의 `price`를 `20000`, `name`을 `"Tee v2"`로 바꾸고 주문을 다시 읽는다
- Then: 주문 항목의 `unitPrice`는 여전히 `10000`, `productName`은 `"Tee"`, `lineTotal`은 `20000`이며, 주문의 `itemsSubtotal`도 변하지 않는다.
- 검증 수단: fake DB 상태 변경 후 재조회 단언.

**AC-ORDER-003** — 주문 번호·상태·금액이 생성 시점에 확정된다 (REQ-ORDER-003 / REQ-ORDER-017)
- Given: 상품 합계가 `35000`인 장바구니가 있다
- When: 주문을 생성한다
- Then: `orderNumber`가 `ORD-YYYYMMDD-` 형식의 비어 있지 않은 문자열이고, `status`가 결제 대기 값이며, `itemsSubtotal === 35000`, `totalAmount === itemsSubtotal + shippingFee`가 성립한다.
- 검증 수단: 생성 결과 객체 단언 + 형식 정규식.

**AC-ORDER-004** — 수량 0 이하 주문 항목이 만들어지지 않는다 (REQ-ORDER-004)
- Given: 장바구니 항목 수량이 `0` 또는 음수인 조작된 상태를 fake DB에 주입한다
- When: 주문 생성을 시도한다
- Then: 주문이 생성되지 않고 거부되며, 수량이 1 미만인 `OrderItem`이 어떤 경우에도 기록되지 않는다.
- 검증 수단: fake DB에 기록된 `OrderItem` 행 전수 검사.

### 주문서 화면

**AC-ORDER-005** — 주문서가 서버에서 게스트 장바구니 내용을 채워 렌더된다 (REQ-ORDER-005)
- Given: 게스트 쿠키 `G1`을 제시하는 렌더 컨텍스트와, 상품 2종이 담긴 `G1`의 장바구니를 반환하도록 모킹한 카트 서비스
- When: `/checkout` 페이지 컴포넌트가 반환한 엘리먼트를 `render()`하고, 별도로 `src/app/checkout/**`·`src/components/checkout/**`를 정적 검사한다
- Then: (a) 두 상품명·수량·단가·상품 합계가 렌더 결과 텍스트에 나타난다. (b) 최초 화면 렌더 경로(서버 컴포넌트와 `OrderSummary`)에 브라우저 측 데이터 요청(`fetch(` 또는 `useEffect` 기반 로딩)이 존재하지 않는다 — 제출 전용 `fetch`는 `CheckoutForm`의 제출 핸들러 안에만 존재한다.
- 검증 수단: (a) jsdom + Testing Library(`cookies()` 모킹). (b) 정적 소스 검사.

**AC-ORDER-006** — 게스트 장바구니가 없으면 양식 대신 안내를 보여 주되, 거짓을 말하지 않는다 (REQ-ORDER-006)
- Given: (i) 게스트 쿠키가 아예 없는 렌더 컨텍스트, (ii) 게스트 쿠키 `G1`은 있으나 `G1`의 장바구니가 비어 있는(`items: []`) 컨텍스트
- When: 각각 `/checkout` 페이지를 렌더한다
- Then: 두 경우 모두 (a) 배송 정보 입력 양식(수령인 이름 입력)이 렌더되지 않고 주문 생성 서비스가 호출되지 않는다. (b) 안내 텍스트가 **방문자의 장바구니가 비어 있다고 단정하지 않는다** — "장바구니가 비어 있습니다" 형태의 단정 문구가 렌더 출력에 존재하지 않고, 서버가 실제로 관측한 사실(이 요청에 연결된 게스트 장바구니를 찾을 수 없음)만 표현된다. (c) **회원 체크아웃이 이번 범위에 없다는 고지**가 렌더 출력에 함께 나타난다. (d) (i)에서 게스트 쿠키를 발급하려는 시도가 없다(응답 쿠키 설정 0건).
- 검증 수단: jsdom + Testing Library `queryBy*` 부재/존재 단언 + 서비스 스파이 미호출 단언 + 금지 문구 부재 단언.
- 근거: 쿠키 없는 요청이 "한 번도 담은 적 없는 게스트"인지 "방금 로그인해 게스트 쿠키가 만료된 회원"인지 서버는 **구별할 수 없다**(design.md §7.1). 그래서 (b)가 필요하다.

**AC-ORDER-007** — 인증 없이 접근·제출 가능 (REQ-ORDER-007)
- Given: 인증 헤더가 없고 게스트 쿠키 `G1`을 가진 요청
- When: `/checkout` 페이지를 렌더하고, `POST /api/orders`를 인증 헤더 없이 호출하며, 별도로 `src/middleware.ts`를 정적 검사한다
- Then: (a) 페이지가 리다이렉트나 `notFound()` 없이 양식을 렌더한다. (b) API가 401·403을 반환하지 않는다. (c) 미들웨어 matcher에 `/checkout`이 포함되지 않는다(§4 불변 조건에 따라 이 파일 변경 0건).
- 검증 수단: (a) 렌더 단언 + `redirect`/`notFound` 스파이 미호출. (b) 라우트 핸들러 응답 상태 단언. (c) 정적 소스 검사.

**AC-ORDER-008** — 수집 항목이 5개로 한정된다 (REQ-ORDER-008 / REQ-ORDER-009)
- Given: 주문서 양식이 렌더되어 있다
- When: 렌더 결과의 입력 요소 전수와 주문 생성 입력 타입·API 라우트 소스를 함께 검사한다
- Then: 입력 항목이 수령인 이름·연락처·우편번호·주소·배송 요청사항 5개뿐이며, 카드번호/유효기간/CVC/이메일/생년월일에 해당하는 입력이 존재하지 않는다. `CreateOrderInput` 타입과 `Order` 모델에도 결제 수단 필드가 없다.
- 검증 수단: `getAllByRole("textbox")` 등 입력 전수 조회 + 정적 소스 검사(`card`, `cvc`, `expiry` 등 토큰 매치 0건).

**AC-ORDER-010** — 필수 배송 정보 누락 시 거부하고 아무 것도 바꾸지 않는다 (REQ-ORDER-010)
- Given: 수령인 이름이 빈 문자열인 제출 본문
- When: `POST /api/orders`를 호출한다
- Then: 400과 함께 `fieldErrors`에 해당 필드 키가 포함되고, 주문이 0건 생성되며, 어떤 상품의 `stock`도 변하지 않고, 장바구니가 그대로 남는다.
- 검증 수단: 응답 단언 + fake DB 전후 스냅샷 비교(주문 수, 재고 값, 카트 항목 수).

### 주문 생성 트랜잭션

**AC-ORDER-011** — 네 가지 효과가 모두 반영된다 (REQ-ORDER-011)
- Given: 재고 `10`인 상품 A를 수량 `3`으로 담은 게스트 장바구니
- When: 유효한 주문을 제출한다
- Then: (a) 주문 1건과 주문 항목 1건이 기록된다. (b) 주문 항목의 `unitPrice`가 A의 현재 가격과 같다. (c) A의 `stock`이 `7`이 된다. (d) 해당 게스트 신원의 장바구니 조회가 빈 카트를 반환한다.
- 검증 수단: 인메모리 fake DB 상태 단언 4건.
- **전제 (fake 롤백)**: 이 AC는 통합 테스트 fake가 `$transaction`을 **콜백 성공 시에만 커밋하도록** 구현했을 때에만 유효하다. fake가 롤백 없이 즉시 반영만 한다면 (a)~(d)의 초록불은 트랜잭션에 대해 아무 것도 말하지 않으므로 **PASS로 계상하지 않고** 미검증으로 기록한다(plan.md §5의 거짓 초록 위험).

**AC-ORDER-012** — 실패 시 부분 반영이 없다 (REQ-ORDER-012)
- Given: 상품 2종이 담긴 게스트 장바구니에서, 두 번째 상품의 재고 차감이 실패하도록 fake를 구성한다
- When: 주문을 제출한다
- Then: (a) 주문이 0건이다. (b) **첫 번째** 상품의 재고가 차감 전 값 그대로다. (c) 장바구니가 그대로 남는다.
- 검증 수단: fake DB 전후 스냅샷 비교. 추가로 정적 검사로 주문 생성의 모든 쓰기가 `prisma.$transaction` 콜백이 넘겨준 클라이언트를 통해서만 일어나는지 확인한다(`prisma.order.`·`prisma.product.update` 같은 트랜잭션 밖 직접 호출 0건). 카트 재조회·삭제도 마찬가지로 design.md §2.1의 **두 함수**에 `tx`를 넘긴 형태여야 한다(싱글턴 기본값으로 호출한 흔적 0건).
- **전제 (fake 롤백)**: AC-ORDER-011과 동일하다 — fake가 롤백을 구현하지 않았다면 (a)~(c)를 PASS로 계상하지 않고 미검증으로 기록한다.
- **실 DB 필요 — 자동 DoD 제외 · `AC-012-EXCL-ROLLBACK`**: PostgreSQL이 실제로 롤백을 수행하는지는 이 하네스로 관측할 수 없다. 이 제외는 Then **(a)·(b)·(c) 전부**를 조건 짓는다(§0). 여기서 판정하는 것은 "서비스가 단일 트랜잭션 콜백 안에서만 쓰고, 실패 시 예외를 던져 콜백을 중단시킨다"까지다.

**AC-ORDER-013** — 재고 부족 시 거부 (REQ-ORDER-013)
- Given: 재고 `2`인 상품을 수량 `5`로 담은 게스트 장바구니
- When: 주문을 제출한다
- Then: (a) 409와 `code: "INSUFFICIENT_STOCK"`, 부족한 상품의 `productId`·`available: 2`가 응답에 포함된다. (b) 주문 0건, 재고 `2` 유지, 장바구니 유지.
- 검증 수단: 응답 본문 단언 + fake DB 스냅샷 비교.
- **실 DB 필요 — 자동 DoD 제외 · `AC-013-EXCL-CONCURRENCY`**: 동시 주문 두 건 중 한 건만 성공하는 직렬화는 실제 DB 잠금이 있어야 관측된다. 이 제외는 위 Then **(a)·(b)를 조건 짓지 않는다** — 둘은 순차 단일 요청만으로 전부 관측되며 자동 DoD에 포함된다. 제외되는 것은 design.md §3이 주장하는 **별개의 동시성 성질**이다. 자동 검증은 재고 차감이 `updateMany` + `stock: { gte: quantity }` 조건 형태로 작성되었고 `count !== 1`이면 실패 경로로 간다는 것까지다(정적 소스 검사 + fake의 `count` 반환 조작).

**AC-ORDER-014** — 확인 금액 불일치 시 거부하고 새 금액을 알린다 (REQ-ORDER-014)
- Given: 주문서 렌더 시 총액이 `30000`이었고, 제출 직전 상품 가격이 올라 서버 재계산값이 `40000`인 상태
- When: 확인 금액 `30000`으로 주문을 제출한다
- Then: 409와 `code: "PRICE_CHANGED"`, `totalAmount: 40000`이 반환되고, 주문 0건·재고 무변경·장바구니 유지다.
- 검증 수단: 응답 단언 + fake DB 스냅샷 비교.

**AC-ORDER-015** — 장바구니가 없거나 비었으면 거부 (REQ-ORDER-015)
- Given: (i) 게스트 쿠키는 있으나 그 신원의 장바구니 행이 없는 요청, (ii) 게스트 쿠키가 없어 신원이 새로 발급된 요청
- When: 각각 주문을 제출한다
- Then: 두 경우 모두 409 `CART_EMPTY`를 반환하고, 주문 0건이며 어떤 상품의 재고도 변하지 않는다. 추가로 (ii)에서는 응답에 게스트 쿠키가 부착된다(다음 담기가 같은 신원으로 이어지도록 — design.md §6.2).
- 검증 수단: 응답 단언 + 응답 쿠키 단언 + fake DB 스냅샷 비교.
- 참고: 이전 판의 "장바구니 항목이 참조하는 상품이 삭제됨"(`PRODUCT_GONE`) 시나리오는 **삭제되었다**. `CartItem.product`가 `onDelete: Cascade`이고 `Product`에 소프트 삭제 컬럼이 없어 그 상태는 실 DB에 존재할 수 없으며, fake에 불일치 상태를 주입해야만 만들어지는 시나리오는 초록불이 아무 것도 보증하지 않는다(design.md §1.5, spec.md §3).

**AC-ORDER-016** — 동일 멱등키 재제출은 주문을 하나만 만든다 (REQ-ORDER-016)
- Given: 재고 `10`인 상품을 수량 `3`으로 담은 게스트 장바구니, 멱등키 `K`
- When: 같은 키 `K`로 주문 제출을 두 번 수행한다
- Then: (a) 두 응답이 같은 `orderId`·`orderNumber`를 반환한다. (b) 주문이 정확히 1건이다. (c) 상품 재고가 `7`이다(두 번 차감되어 `4`가 되지 않는다).
- 검증 수단: 두 응답 비교 + fake DB 행 수·재고 단언.
- **실 DB 필요 — 자동 DoD 제외 · `AC-016-EXCL-UNIQUE-RACE`**: 동시에 도착한 두 요청이 `@unique` 제약으로 직렬화되는 2차 방어(design.md §5)는 실제 DB에서만 관측된다. 이 제외는 위 Then **(a)·(b)·(c)를 조건 짓지 않는다** — 셋은 순차 재제출로 전부 관측되며 자동 DoD에 포함된다. 자동 검증은 순차 재제출(1차 방어)과, unique 위반 예외를 fake로 주입했을 때 최초 주문을 재조회해 반환하는 경로까지다.

### 완료 화면 및 경계

**AC-ORDER-018** — 완료 화면이 주문 내용과 결제 미완료를 알린다 (REQ-ORDER-018)
- Given: 방금 생성된 게스트 주문과, 그 주문을 만든 게스트 쿠키를 가진 요청
- When: `/checkout/complete/{orderId}`를 렌더한다
- Then: 주문 번호, 각 주문 항목의 상품명·수량·주문 시점 단가, 총 금액, 배송지 요약이 나타나고, 결제가 아직 완료되지 않았다는 취지의 안내가 나타난다.
- 검증 수단: jsdom + Testing Library 렌더 단언(`cookies()` 모킹).

**AC-ORDER-019** — 결제 연동 흔적이 없다 (REQ-ORDER-019)
- Given: 이 SPEC이 추가·수정한 전체 산출물
- When: 소스와 설정을 정적 검사한다
- Then: (a) `package.json`에 결제 관련 신규 의존성이 없다. (b) `.env.example`에 PG 관련 신규 변수가 없다. (c) 소스 어디에도 외부 결제 엔드포인트 호출이 없다. (d) 주문 상태를 결제 완료로 전이시키는 코드 경로가 존재하지 않는다.
- 검증 수단: 정적 소스·설정 검사(diff 기준).

**AC-ORDER-020** — 타인의 주문은 열람되지 않는다 (REQ-ORDER-020)
- Given: 게스트 `G1`이 만든 주문 `O`
- When: (i) 다른 게스트 쿠키 `G2`로, (ii) 아무 신원 없이 `/checkout/complete/{O.id}`를 각각 렌더하고, 별도로 (iii) `src/app/checkout/complete/**`를 정적 검사한다
- Then: (a) (i)·(ii) 두 경우 모두 `notFound()` 경로로 진입하고(403이 아니다), 주문 번호·상품명·배송지 어느 것도 렌더 출력에 나타나지 않는다. (b) (iii)에서 `headers(`·`authorization`(대소문자 무시) 토큰의 매치가 **0건**이다.
- 검증 수단: (a) `notFound` 스파이 호출 단언 + 렌더 출력 부재 단언(`cookies()` 모킹). (b) 정적 소스 검사(토큰 매치 0건).
- 참고: 회원 Bearer 토큰만 제시한 요청이 열람에 실패하는 것은 부작용이 아니라 설계다(design.md §6.3). 다만 렌더 하네스에는 `Request`가 없어 토큰 제시 자체를 구성할 수 없으므로, 그 성질은 (b)의 정적 검사로 고정한다 — 완료 화면에 `Authorization`을 읽는 코드 경로가 아예 없다는 것이 실제 증거다.
- **범위 경계**: 이 AC가 다루는 것은 **완료 화면(서버 렌더 경로)** 하나뿐이다. REQ-ORDER-020이 함께 금지하는 **API 주문 조회 경로**(멱등키 재제출로 주문을 돌려받는 경로)는 이 AC가 관측하지 않으며, **AC-ORDER-023**이 다룬다. 두 경로를 한 AC로 묶어 읽지 말 것.

**AC-ORDER-021** — 서버 렌더 경로가 게스트 쿠키만 읽고 자체 신원 판정을 만들지 않는다 (REQ-ORDER-005 / REQ-ORDER-007)
- Given: (i) `guest_cart_id` 쿠키만 있는 렌더 컨텍스트, (ii) 쿠키가 하나도 없는 렌더 컨텍스트
- When: 두 경우 각각 `/checkout` 서버 컴포넌트를 렌더하고, 별도로 `src/app/checkout/**`(하위 `complete/[orderId]` 포함)를 정적 검사한다
- Then: (a) (i)은 그 쿠키 값의 게스트 신원으로 장바구니가 조회된다. (b) (ii)는 카트 서비스를 호출하지 않고 곧바로 AC-ORDER-006의 안내 화면으로 귀결되며, 쿠키를 발급하려 시도하지 않는다. (c) 서버 렌더 소스에 **다음 토큰의 매치가 0건**이다 — `verifyAccessToken`, `resolveCartIdentity`, `readGuestCartId`, `getCookieValue`, `generateGuestCartId`, `new Request(`. (d) 쿠키 이름이 `@/lib/auth/guest-identity`의 `GUEST_CART_COOKIE_NAME`을 import해 쓰이며, `"guest_cart_id"` 문자열 리터럴의 매치가 0건이다. (e) `src/features/orders/lib/server-identity.ts` 파일이 **존재하지 않는다**.
- 검증 수단: (a)(b) `next/headers`의 `cookies()`를 모킹한 렌더 단언 + 카트 서비스 스파이. (c)(d) 정적 소스 검사(토큰·리터럴 매치 0건 + import 존재 단언). (e) 파일 부재 확인.
- 근거: 읽기 경로가 판정하는 것이 없어야 authorization 표면이 갈라지지 않는다(design.md §6.1). (e)는 회원 신원을 위해 존재했던 어댑터가 되살아나지 않도록 고정한다.

**AC-ORDER-022** — 회원 자격 증명을 제시한 주문 제출은 거부된다 (REQ-ORDER-021)
- Given: 재고 `10`인 상품이 담긴 장바구니가 존재하는 상태에서, `Authorization: Bearer <유효 토큰>`을 붙인 `POST /api/orders` 요청(본문은 그 외 전부 유효)
- When: 요청을 처리한다
- Then: (a) 409와 `code: "MEMBER_CHECKOUT_UNSUPPORTED"`가 반환된다(401·403이 아니다). (b) 주문이 0건 생성된다. (c) 어떤 상품의 `stock`도 변하지 않는다. (d) 어떤 장바구니도 삭제되지 않는다. (e) `prisma.$transaction`이 호출되지 않는다 — 거부는 트랜잭션 진입 전에 일어난다.
- 검증 수단: 응답 단언 + fake DB 전후 스냅샷 비교 + `$transaction` 스파이 미호출 단언.
- 이 AC가 왜 도달 가능한 경로를 검사하는가: 브라우저 폼 제출은 토큰을 붙일 수 없지만 `POST /api/orders`는 공개 엔드포인트이므로 유효 토큰을 가진 누구나 직접 호출할 수 있다. 신뢰 경계의 실제 가드이며, 이 SPEC의 게스트 전용 경계를 코드로 강제하는 지점이다(spec.md §3 첫 항목).

**AC-ORDER-023** — 멱등키 재제출 경로가 타인의 주문을 돌려주지 않는다 (REQ-ORDER-020 / REQ-ORDER-016)
- Given: 게스트 `G1`이 멱등키 `K`로 만든 주문 `O`가 존재하고, `O`의 배송지에는 수령인 이름·연락처·우편번호·주소·배송 요청사항이 들어 있다. 별개의 게스트 `G2`는 자기 장바구니를 가지고 있다
- When: (i) `G2`의 게스트 쿠키로 같은 멱등키 `K`를 붙여 `POST /api/orders`를 호출하고, (ii) 게스트 쿠키가 없는 요청으로 같은 키 `K`를 붙여 호출한다
- Then: (a) 두 경우 모두 응답 본문에 `O`의 어떤 내용도 나타나지 않는다 — `O`의 `orderId`·`orderNumber`·주문 항목·총액은 물론, **배송 PII 5개 값(수령인 이름·연락처·우편번호·주소·배송 요청사항) 어느 것도 응답 어디에도 문자열로 존재하지 않는다**. (b) `O`는 여전히 1건이며 그 어떤 필드도 수정되지 않고, `O`의 귀속 게스트는 `G1` 그대로다. (c) `G1`이 자신의 쿠키로 같은 키 `K`를 다시 제출하면 여전히 `O`를 그대로 돌려받는다 — 이 AC는 AC-ORDER-016의 정상 재제출 동작을 좁히지 않는다.
- 검증 수단: 응답 본문 전수 문자열 검사(배송 PII 5개 값과 `O.orderNumber`·`O.id`의 매치 0건) + fake DB의 `O` 행 전후 스냅샷 비교 + AC-ORDER-016 시나리오 재실행.
- **이 AC가 정하지 않는 것**: `G2`의 요청을 *어떻게* 처리할지 — 키 충돌로 거부할지, 그 키를 `G2`의 것이 아닌 것으로 보고 별개 주문으로 진행할지 — 는 설계 판단이며 여기서 고정하지 않는다. 이 AC가 고정하는 것은 관측 가능한 성질 하나뿐이다: **멱등키를 아는 것만으로는 타인의 주문에 닿을 수 없다.**
- 근거: 사후 보안 감사(sync-auditor `--security --deep`)가 재현한 High 등급 접근 제어 결함 F1 — 멱등키 재제출 경로가 되돌려주는 주문이 *요청한 게스트의 것인지* 확인하지 않아, 남의 키를 아는 게스트에게 배송 PII를 포함한 주문 전체가 노출됐다. 그 결함 라인은 테스트 커버리지 안에 있었지만 **교차 게스트 질문을 받은 적이 없었다** — AC-ORDER-020이 완료 화면만 다뤘기 때문이다(감사 F2). 초록불 아래로 버그가 지나간 자리가 여기이므로, 화면과 API 두 경로를 각각 별도 AC로 고정한다.

## §1.5 추적성 (REQ → AC)

AC 번호는 대응 REQ 번호를 따라가되, 두 요구사항은 별도 AC를 두지 않고 인접 AC에 흡수했다. 따라서 AC 번호에 `009`와 `017`이 없는 것은 누락이 아니라 아래 매핑 때문이다.

| REQ | AC | 비고 |
|---|---|---|
| REQ-ORDER-001 / 002 / 003 / 004 | AC-001 / 002 / 003 / 004 | 1:1 |
| REQ-ORDER-005 / 006 / 007 / 008 | AC-005 / 006 / 007 / 008 | 1:1 |
| **REQ-ORDER-009** (결제 수단 미수집) | **AC-008** | 수집 항목 전수 검사와 같은 관측으로 판정되므로 통합 |
| REQ-ORDER-010 ~ 016 | AC-010 ~ 016 | 1:1 |
| **REQ-ORDER-017** (초기 상태 = 결제 대기) | **AC-003** | 주문 생성 시점 확정값 검사와 같은 관측이므로 통합 |
| REQ-ORDER-018 / 019 / 020 | AC-018 / 019 / 020 | 1:1 |
| REQ-ORDER-005 / 007 (재검증) | **AC-021** | 서버 렌더 경로가 게스트 쿠키만 읽고 신원 판정을 자체 구현하지 않는지 고정 |
| **REQ-ORDER-021** (회원 제출 거부) | **AC-022** | 1:1 |
| REQ-ORDER-020 / 016 (재검증) | **AC-023** | AC-020이 완료 **화면**만 다루므로, REQ-ORDER-020이 함께 금지하는 **API 주문 조회 경로**(멱등키 재제출)를 별도 AC로 고정 — 사후 보안 감사 F1/F2 |

REQ 21개 전부가 최소 하나의 AC에 대응하며, AC 없이 남은 REQ는 없다. AC는 총 **21개**(`001~008`, `010~016`, `018~023`)로 Tier L 상한 25개 이내다.

> **AC-021과 AC-023은 REQ 번호를 새로 만들지 않는다.** 둘 다 기존 REQ가 이미 요구하던 성질을 *다른 표면에서* 다시 고정하는 재검증 AC다. AC 번호가 REQ 번호를 따라가는 원칙의 예외이며, 그 예외인 이유를 위 표의 비고에 남긴다.

## §2. 엣지 케이스

| 케이스 | 기대 동작 | 관련 AC |
|---|---|---|
| 장바구니에 같은 상품이 두 항목으로 존재 | `@@unique([cartId, productId])` 때문에 발생 불가 — 방어 코드 불필요 | — |
| 재고가 정확히 주문 수량과 같음(`stock === quantity`) | 성공하고 재고가 `0`이 된다(`gte` 조건이므로 경계 포함) | AC-011 |
| 배송 요청사항 미입력 | 선택 항목이므로 성공, `deliveryMemo`는 `null` | AC-008 |
| 제출 본문이 JSON이 아님 | 400 `Invalid request body`(기존 카트 라우트와 동일 형태), 아무 것도 변경 없음 | AC-010 |
| 확인 금액 필드 자체가 없음 | 400(형식 오류)으로 처리 — 대조를 건너뛰지 않는다 | AC-010 |
| 회원 토큰과 게스트 쿠키를 함께 보냄 | `resolveCartIdentity()`가 회원으로 해석 → 409 `MEMBER_CHECKOUT_UNSUPPORTED`. 쿠키가 있어도 게스트로 강등해 주문하지 않는다 | AC-022 |
| 로그인한 회원이 `/checkout`에 진입 | 토큰도 게스트 쿠키도 서버에 도달하지 않으므로 안내 화면. 안내는 장바구니가 비었다고 단정하지 않고 회원 체크아웃 부재를 고지한다 | AC-006 |
| 트랜잭션 진행 중 다른 세션이 상품을 삭제 | `updateMany`가 0행을 갱신해 `INSUFFICIENT_STOCK` 경로로 롤백된다. 정합성은 안전하고 메시지만 부정확하며, 이는 수용된 잔여 위험이다(design.md §9) | AC-013 |
| 주문 후 완료 화면 새로고침 | 같은 내용이 다시 표시된다(주문 조회는 부수효과가 없다) | AC-018 |
| 게스트 쿠키 만료 후 완료 화면 재방문 | `notFound()` — 재방문 조회는 이 SPEC 범위 밖(spec.md §3) | AC-020 |
| 다른 게스트의 멱등키를 알아내 그 키로 주문을 제출 | 그 키로 만들어진 주문의 내용(배송 PII 포함)이 응답에 나타나지 않는다. 키를 아는 것은 주문에 닿을 자격이 아니다 | AC-023 |
