# SPEC-E2E-001 — 인수 기준

> 각 항목은 Given-When-Then 형식의 **이진 판정** 기준이다. 통과/실패 외의 결과를 남기지 않는다.
> 요구사항 본문(GEARS)은 `spec.md` §2에 있다 — 여기서 되풀이하지 않는다.

## §A. 하네스 기반

### AC-E2E-001 — E2E 스위트가 실제 브라우저·실제 서버로 실행된다

- **Given** 저장소가 체크아웃되어 있고 필수 환경 변수와 시드된 데이터베이스가 준비된 상태에서
- **When** `npm run test:e2e` 를 실행하면
- **Then** Playwright가 애플리케이션 서버를 기동하고 Chromium으로 시나리오를 실행하며, 명령의 종료 코드가 `0` 이다

추적: REQ-E2E-001, REQ-E2E-002, REQ-E2E-003

### AC-E2E-002 — 기존 Vitest 스위트가 영향을 받지 않는다

- **Given** E2E 하네스가 도입된 상태에서
- **When** `npm test` 를 실행하면
- **Then** 수집되는 테스트 파일 목록이 도입 이전과 동일하고, `e2e/` 아래의 어떤 파일도 Vitest에 수집되지 않으며, 종료 코드가 `0` 이다

추적: REQ-E2E-002

### AC-E2E-003 — 필수 환경 변수 부재는 조기에 실패한다

- **Given** `NEXT_PUBLIC_PG_CLIENT_KEY` 가 설정되지 않은 상태에서
- **When** E2E 스위트를 시작하면
- **Then** 스위트는 첫 시나리오를 실행하기 전에 실패하고, 실패 메시지가 누락된 변수의 이름을 담는다

추적: REQ-E2E-004

## §B. Toss 결제 모킹

### AC-E2E-004 — 어떤 실행에서도 Toss 호스트에 요청이 나가지 않는다

- **Given** 모든 시나리오에 Toss 호스트 감시 라우트가 설치된 상태에서
- **When** 전체 E2E 스위트를 실행하면
- **Then** `js.tosspayments.com` 및 `api.tosspayments.com` 으로 향한 요청이 **0건**이며, 감시 라우트가 한 번이라도 발동하면 해당 시나리오는 실패한다

추적: REQ-E2E-005
비고: 이 기준은 **관찰 가능한 결과**만 고정한다. 서버 측 가로채기 메커니즘은 `plan.md` §B가 확정한 undici 전역 디스패처 모킹 하나이며(프로덕션 소스 변경 0줄), 베이스 URL 환경 변수 이음매는 기각됐다 — 이 AC는 그 확정을 완화하지 않으며, 기각된 이음매를 되살린 구현은 이 AC를 만족한 것으로 보지 않는다.

### AC-E2E-005a — 스텁 SDK가 성공 모드에서 애플리케이션이 만든 successUrl 로 이동한다

- **Given** 결제 대기(`pending_payment`) 상태의 주문 완료 화면이 열려 있고 스텁이 성공 모드인 상태에서
- **When** 결제 트리거를 누르면
- **Then** 브라우저는 `PayButton` 이 구성한 `successUrl`(`/api/payments/confirm`)로 이동하며, 그 URL에 `paymentKey`, `orderId`, `amount` 질의 파라미터가 실려 있다

추적: REQ-E2E-006, REQ-E2E-007

### AC-E2E-005b — 스텁 SDK가 실패 모드에서 애플리케이션이 만든 failUrl 로 이동한다

- **Given** 같은 화면에서 스텁이 실패 모드인 상태에서
- **When** 결제 트리거를 누르면
- **Then** 브라우저는 `PayButton` 이 구성한 `failUrl`(`/checkout/complete/{orderId}?payment_failed=1`)로 이동한다

추적: REQ-E2E-007

## §C. 여정 — 해피 패스

### AC-E2E-006 — 장바구니 담기가 장바구니 화면에 반영된다

- **Given** 장바구니가 비어 있는 새 브라우저 컨텍스트에서
- **When** 상품 상세 화면에서 상품을 장바구니에 담고 `/cart` 로 이동하면
- **Then** 장바구니 화면에 그 상품이 한 줄로 표시되고, 빈 장바구니 화면은 표시되지 않는다

추적: REQ-E2E-008

### AC-E2E-007 — 유효한 주문서 제출이 주문을 만들고 완료 화면으로 이동한다

- **Given** 상품이 담긴 장바구니로 `/checkout` 에 진입한 상태에서
- **When** 필수 다섯 필드 중 required 항목을 모두 유효하게 채우고 제출하면
- **Then** 브라우저는 `/checkout/complete/{orderId}` 로 이동하고, 그 화면이 결제 대기 상태와 결제 트리거를 표시한다

추적: REQ-E2E-009

### AC-E2E-008 — 모킹된 결제 성공이 결제 완료 상태에 도달한다

- **Given** AC-E2E-007이 도달시킨 결제 대기 화면에서 스텁이 성공 모드인 상태에서
- **When** 결제를 완료하면
- **Then** 브라우저는 `/checkout/complete/{orderId}` 에 `payment_failed` 파라미터 없이 안착하고, 화면이 결제 완료 상태를 표시하며, 결제 트리거가 더 이상 표시되지 않는다

추적: REQ-E2E-010

## §D. 여정 — 실패·엣지 경로

### AC-E2E-009 — 결제 실패 후 재시도가 성공에 도달한다

- **Given** 결제 대기 화면에서 스텁이 실패 모드인 상태에서
- **When** 결제를 시도하면
- **Then** 브라우저는 `/checkout/complete/{orderId}?payment_failed=1` 에 있고 재시도 안내와 결제 트리거가 함께 표시되며,
- **And When** 스텁을 성공 모드로 바꾸고 결제를 다시 시도하면
- **Then** 화면이 결제 완료 상태에 도달한다

추적: REQ-E2E-011

### AC-E2E-010 — 빈 장바구니로 체크아웃에 진입하면 주문서가 열리지 않는다

- **Given** 장바구니가 비어 있는 브라우저 컨텍스트에서
- **When** `/checkout` 으로 직접 이동하면
- **Then** 체크아웃 불가 화면이 표시되고, 주문서 입력 필드는 표시되지 않는다

추적: REQ-E2E-012

### AC-E2E-011 — 필수 필드를 비운 제출은 거부된다

- **Given** 상품이 담긴 장바구니로 `/checkout` 에 진입한 상태에서
- **When** 필수 필드 하나를 비운 채 제출하면
- **Then** 브라우저는 `/checkout` 에 머무르고, `/checkout/complete/` 로 이동하지 않는다

추적: REQ-E2E-013

### AC-E2E-012 — 유효한 쿠폰 적용이 주문 요약에 반영된다

- **Given** 상품이 담긴 장바구니로 `/checkout` 에 진입하고 유효한 쿠폰 코드가 준비된 상태에서
- **When** 쿠폰 코드를 입력하고 적용하면
- **Then** 주문 요약의 할인 표시와 결제 예정 금액이 적용 이전과 다른 값으로 갱신되고, 이 시점까지 주문은 생성되지 않는다

추적: REQ-E2E-014

## §E. 스위트 품질

### AC-E2E-013 — 시나리오가 서로 독립적이다

- **Given** 전체 E2E 스위트가 존재하는 상태에서
- **When** 시나리오 실행 순서를 뒤집어 실행하면
- **Then** 모든 시나리오가 동일하게 통과한다

추적: REQ-E2E-015

### AC-E2E-014 — 단언이 구매자 관찰 가능한 결과에만 걸린다

- **Given** 작성된 모든 시나리오에 대해
- **When** 단언 대상을 검토하면
- **Then** 모든 단언이 렌더된 텍스트 · URL · 컨트롤 표시 여부 중 하나이며, 애플리케이션 내부 모듈 상태를 직접 읽는 단언이 없다

추적: REQ-E2E-015

### AC-E2E-015 — 동시 행위자에 의존하는 시나리오가 존재하지 않는다

- **Given** 작성된 모든 시나리오에 대해
- **When** 각 시나리오의 행위자 수를 검토하면
- **Then** 두 개 이상의 동시 행위자를 기동하거나 그 인터리빙에 결과가 의존하는 시나리오가 **0건**이다

추적: REQ-E2E-016

## §F. 범위 밖 — 이 스위트가 검증하지 **않는** 것

아래는 누락이 아니라 확정된 제외다(근거는 `spec.md` §3). 후속 독자가 공백으로 오인하지 않도록 인수 기준 레벨에서도 명시한다.

- **동시성 · 재고 경합 · 롤백**: 두 행위자의 인터리빙에 결과가 달라지는 시나리오는 이 스위트에 **없어야 한다**. 존재하면 REQ-E2E-016 위반이며, AC-E2E-015가 이를 통과/실패로 판정한다. 소유: SPEC-ORDER-002.
- **`/orders/lookup` 재방문 화면**: 이 스위트의 여정은 `/checkout/complete/{orderId}` 에서 끝난다. 소유: SPEC-ORDER-003.
- **로그인 회원 결제**: 애플리케이션에 동작하는 회원 결제 경로가 존재하지 않는다(`409 MEMBER_CHECKOUT_UNSUPPORTED`). 검증할 대상 자체가 없다.
- **`/admin/*` 도달 가능성**: 미들웨어 우회 사례는 이 SPEC의 동기일 뿐 검증 대상이 아니다.
- **CI에서의 E2E 실행**: `.github/workflows/ci.yml` 은 이 SPEC에서 수정되지 않는다.
