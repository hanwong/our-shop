# Plan: SPEC-ORDER-003 — 게스트 주문 재방문 조회와 주문 상태 표시

## §0. 결정 기록

### 확정 — 카드 `t8`을 셋으로 쪼갠다

카드 `t8`("배송지 관리와 주문 배송 상태 조회")은 세 능력을 한 문장으로 묶고 있으나, 조사 결과 셋은 서로 다른 기반을 요구하며 그중 지금 만들 수 있는 것은 하나뿐이다(spec.md §2). 이 SPEC은 그 하나만 인수하고, 나머지 둘은 spec.md §3에서 제외하며 별도 SPEC 후보로 세운다.

| 능력 | 이 SPEC | 넘기는 곳 | 선행 조건 |
|---|---|---|---|
| 게스트 주문 재방문 조회 | **인수** | — | 없음(지금 가능) |
| 배송지 주소록 관리 | 제외 | 백로그 카드 `t23` (회원 체크아웃 SPEC 또는 `SPEC-ADDRESS-001` 후보) | 백로그 `t18` 또는 회원 체크아웃 |
| 배송(이행) 상태 기계 | 제외 | 백로그 카드 `t24` (`SPEC-SHIPPING-001` 후보) | 백로그 `t12`(전이 주체) |

이 쪼갬은 선행 SPEC의 판단을 따른 것이다. SPEC-ORDER-001 §3은 카드가 묶은 두 능력을 **서로 다른 두 개의 제외 절**("주문 내역 조회 및 배송 상태 화면", "주소 검색 API 및 다중 배송지")로 나눠 넘겼다.

### 확정 — SPEC ID를 `SPEC-SHIPPING-001`에서 `SPEC-ORDER-003`으로 바꾼다

잠정 ID는 `SPEC-SHIPPING-001`이었으나, 실제로 작성하는 범위에 배송 도메인 산출물이 하나도 없다. 새 모델도, 새 상태값도, 운송장 필드도 만들지 않는다. `module`은 `src/features/orders`이고, 확장하는 것은 `order-repository.ts`와 주문 화면이다. 자기 §3에서 배송 상태 기계를 제외하는 SPEC에 `SHIPPING` 이름을 붙이면 ID가 본문이 부정하는 것을 약속하게 된다.

**되돌리기 조건**: 아래 결정 2가 (B)로 확정되어 이행 상태값과 `Shipment` 모델이 모두 범위 밖으로 확정되었으므로, 이 조건은 현재 성립하지 않는다. 다만 후속 변경으로 이행 상태값이나 `Shipment` 모델이 이 SPEC의 범위로 들어온다면, 이 SPEC은 `SPEC-SHIPPING-001`로 다시 세우고 재계획한다. 지금은 `SPEC-ORDER-003` ID가 확정이다.

**대가**: 도메인을 잇는 결과로 REQ·AC 번호가 001부터 시작하지 못하고 기존 `ORDER` 번호를 이어받는다(REQ는 034부터, AC는 037부터). 이는 SPEC-ORDER-002가 SPEC-ORDER-001의 021 다음인 022부터 시작한 선례를 따른 것이다.

### 확정 — 범위를 가르는 결정 3건 (사용자 확정, 2026-09-03)

이전에 열려 있던 세 가지 질문은 2026-09-03 사용자 결정으로 모두 닫혔다. 셋 다 조사가 내놓았던 권고와 같은 선택으로 확정되었으므로, 아래 근거와 대가는 그대로 유효하다. **run-phase 진입을 막는 열린 항목은 이제 없다.**

**결정 1 — 배송지 주소록은 이 SPEC에서 완전히 제외한다 (확정: C)**

- **확정 내용**: 저장된 배송지 목록, 배송지 추가·수정·삭제, 기본 배송지 지정, `Address` 모델 신설, 우편번호 검색 API 연동을 **이 SPEC에서 전부 제외한다**. 회원 전용 주소록을 포함하는 (A)와 브라우저 저장소로 마지막 배송지만 기억하는 (B)는 모두 기각되었다.
- **확정 근거**: `Address` 모델 없음. `Order.userId` 없음(`guestId` NOT NULL). `src/app/` 아래에 `account`·`mypage`·`profile` 계열 경로가 **하나도 없다** — (A)의 우회로로 검토했던 "클라이언트 인증만으로 도달하는 마이페이지 경로 재사용"은 재사용할 대상이 없어 성립하지 않는다. `product.md` 핵심 기능 1~6과 In-scope 목록에도 주소록이 없다.
- **받아들인 대가**: 카드 `t8` 제목의 절반이 이 SPEC에서 빠진다. 비회원 주문자는 다음 주문에서 배송지를 다시 입력해야 하며, 이 불편은 회원 신원 기반이 설 때까지 남는다. 그 대신 이 SPEC은 지금 온전히 완결되고, 주소록은 소유자가 생긴 뒤 제대로 설계된다. (A)를 택했다면 Tier M → L, 산출물 3종 → 5종, `depends_on`에 `SPEC-AUTH-001` 추가, REQ 12건 → 20건 내외로 커졌을 것이다.
- **넘긴 곳 — 백로그 카드 `t23`**: "배송지 주소록 관리(회원 전용) — Address 모델·userId FK·마이페이지 화면 전부 없음, 회원 체크아웃/신원 기반(백로그 `t18`)이 먼저 서야 함. `t8`에서 분리됨". 선행 조건은 `t18` 해소 또는 회원 체크아웃 도입이다.

**결정 2 — 새 이행 상태값을 도입하지 않는다 (확정: B)**

- **확정 내용**: 카드 제목의 "배송 상태"는 **기존 `OrderStatus` 3종(`pending_payment`/`paid`/`cancelled`)의 재방문 조회**를 뜻한다. `preparing`/`shipped`/`delivered` 같은 이행 상태값을 추가하는 (A)와 운송장 번호 표시 필드만 더하는 (C)는 모두 기각되었다. 이 SPEC은 스키마를 건드리지 않는다.
- **확정 근거**: `OrderStatus`는 정확히 3종이다(`prisma/schema.prisma:214-218`). `Shipment` 모델, 운송장 컬럼, 배송사 필드는 스키마 어디에도 없다. `PaymentAuditLog`도 이행 개념을 암시하지 않는다 — 그 `previousStatus`/`newStatus`는 같은 `OrderStatus` 3종을 참조한다. **이행을 암시하는 흔적은 저장소에 하나도 없다.** `product.md`는 배송 상태 관리를 관리자의 일로 규정하지만(20행, 핵심 기능 #6) 관리자 백오피스는 백로그 `t12`로 아직 계획되지 않았다.
- **받아들인 대가**: 사용자는 "결제됨" 다음의 진행 상황(준비 중인지, 발송되었는지)을 이 화면에서 알 수 없다. 이 침묵은 의도된 것이다 — 전이 주체가 없는 상태값을 만들면 모든 주문이 영원히 초기값에 머무는 죽은 컬럼이 되고, 화면은 정직하지 않은 정보를 보이게 된다. 없는 정보를 안 보이는 편이 틀린 정보를 보이는 편보다 낫다.
- **넘긴 곳 — 백로그 카드 `t24`**: "배송 이행 상태 기계(준비중/배송중/배송완료) — 새 상태값·전이 주체(관리자 백오피스, 백로그 `t12`) 둘 다 미계획. `t8`에서 분리됨, SPEC-SHIPPING-001 후보". 선행 조건은 전이 주체 확정 — 실질적으로 `t12` 관리자 주문 관리다.

**결정 3 — 대조 비밀값은 주문 번호 + 수령인 연락처다 (확정: A)**

- **확정 내용**: 게스트 재방문 조회는 **주문 번호(`orderNumber`)와 수령인 연락처(`recipientPhone`) 두 값이 같은 하나의 주문에서 일치할 때에만** 열린다. 수령인 이름을 쓰는 (B), 조회 전용 토큰을 발급하는 (C), 이메일 링크를 보내는 (D)는 모두 기각되었다.
- **확정 근거**: 주문이 보유한 필드는 `orderNumber`(유니크), `recipientName`, `recipientPhone`, `postalCode`, `address`, `deliveryMemo`뿐이다. **이메일은 수집하지 않는다** — SPEC-ORDER-001이 개인정보 최소 수집 원칙에 따라 명시적으로 배제했고(§3 "주문 확인 알림"), 따라서 (D)는 이 SPEC이 이메일 수집을 새로 도입하지 않는 한 불가능하다. 연락처는 이름보다 추측 공간이 넓고, 주문자가 이미 입력했으므로 별도 발급·보관 장치가 필요 없다. (C)는 가장 강하지만 토큰을 잃어버린 사람에게 복구 수단이 없고, 그 복구 수단이 결국 (A)가 된다.
- **기존 경로에 결함은 없다**: `findOrderForGuest()`는 `findFirst({ where: { id, guestId } })`로 소유자 조건을 쿼리에 담으므로, 식별자를 추측해도 타인의 주문이 열리지 않는다. **열거 위험은 이 SPEC이 새로 만드는 진입 경로에서 처음 생긴다.**
- **받아들인 대가 — 없애지 못하는 잔여 위험**: 주문 번호와 수령인 연락처를 모두 아는 사람은 그 주문을 열 수 있다. 이는 채택한 대조 방식의 정의상 성질이며, REQ-ORDER-036(구별 불가능한 실패)과 REQ-ORDER-037(반복 실패 제한)으로 표면을 낮출 뿐 제거하지 못한다. §6에 잔여 위험으로 기록한다.
- **M1에서 확인할 것**: `orderNumber` 형식이 순차적이면 이 방식의 위험이 커진다 — M1 착수 시 생성 방식을 확인해 추측 가능하면 형식 변경을 별도 항목으로 올린다.

## §1. 핵심 설계 결정 — 조회 권한의 형태 (되돌리기 가장 어려운 결정)

이 SPEC이 만드는 것 중 나중에 바꾸기 가장 비싼 것은 **무엇이 주문을 열게 하는가**이다. 한번 공개된 조회 규칙은 사용자의 기대가 되고, 느슨하게 시작하면 조이는 것이 사용자에게 기능 회수로 보인다.

### 채택: 소유자 조건을 쿼리에 담는다 (기존 방식의 확장)

새 조회도 `findFirst({ where: { orderNumber, recipientPhone } })` 형태로, **대조 조건을 쿼리 자체에 담는다**. 주문을 먼저 가져온 뒤 애플리케이션에서 비교하는 형태를 쓰지 않는다.

- 근거: SPEC-ORDER-001이 `findOrderForGuest()`에서 세운 선례다(`order-repository.ts:107-112`, `page.tsx:18-20` 주석 "KNOWING THE ORDER ID IS NOT ENOUGH"). "가져온 뒤 안 보여주기"는 어딘가에서 분기를 빠뜨리면 노출이 되지만, "조건에 맞지 않으면 애초에 가져오지 않기"는 그런 형태의 실수가 불가능하다.
- 결과: 조회 결과가 `null`인 경우가 "없는 주문"과 "대조 실패"를 자연히 구별하지 못한다 — REQ-ORDER-036이 요구하는 성질이 설계에서 공짜로 나온다.

### 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 주문 번호만으로 조회 | REQ-ORDER-020(선행 SPEC)을 정면으로 위반한다. 주문 번호는 화면·영수증에 노출되는 값이다 |
| 주문을 가져온 뒤 연락처 비교 | 노출 분기를 빠뜨릴 수 있는 형태. 위 선례가 이미 거부한 형태다 |
| 실패를 404와 403으로 나눔 | 403이 "그 주문은 실재한다"를 알려준다. `page.tsx:22-24`가 같은 이유로 이미 거부했다 |
| 조회 전용 토큰 발급 | 분실 시 복구 수단이 결국 연락처 대조가 된다. 두 경로를 다 만드는 값을 치를 근거가 아직 없다 |

## §2. 실패를 어떻게 보이게 할 것인가 (사용자가 실제로 겪는 것)

REQ-ORDER-036은 실패가 구별되지 않기를 요구하지만, 그렇다고 사용자를 막막하게 두어서는 안 된다. 두 층으로 나눈다.

- **형식 검증 실패**(빈 입력, 주문 번호 형식 불일치, 연락처 형식 불일치)는 **구체적으로** 알린다. 이 단계는 아직 어떤 주문도 조회하지 않았으므로 주문의 실재 여부를 흘리지 않는다(REQ-ORDER-043).
- **대조 실패**는 **하나의 문구로 통일**한다. "주문 번호 또는 연락처가 일치하지 않습니다" — 어느 쪽이 틀렸는지, 그 주문 번호가 실재하는지 알 수 없다(REQ-ORDER-036).

응답 시간도 구별 신호가 될 수 있다. 대조 실패 경로가 조회를 건너뛰어 빨리 끝나면 그 자체가 정보다. 두 경로 모두 동일하게 한 번의 쿼리를 수행하도록 만든다.

## §3. 마일스톤 (되돌리기 어려운 순서)

### M1 — 조회 권한 규칙과 실패 표면 (우선순위 High)

가장 되돌리기 어려운 결정을 먼저 굳힌다.

- `order-repository.ts`에 `findOrderByNumberAndPhone(orderNumber, recipientPhone)` 추가 — 대조 조건을 `where`에 담는 단일 조회.
- `order-service.ts`에 조회 유스케이스 추가 — 형식 검증 → 조회 → 통일된 실패 반환.
- 대조 실패와 미존재가 호출자에게 같은 값으로 보이는지 단위 테스트로 고정.
- 대응: REQ-ORDER-034, 035, 036, 043.

### M2 — 조회 화면과 진입 경로 (우선순위 High)

사용자가 보는 것이므로 M1 다음으로 바꾸기 비싸다.

- 조회 입력 화면(주문 번호 + 연락처)과 조회 결과 화면 신설.
- 결과 화면은 완료 화면의 표시 항목을 재사용하되, 결제 버튼과 결제 실패 배너는 **싣지 않는다**(읽기 전용).
- 게스트 쿠키가 유효하고 주문 귀속과 일치하면 대조 없이 열리는 경로(REQ-ORDER-044).
- 대응: REQ-ORDER-038, 040, 041, 042, 044.

### M3 — 노출 금지 항목과 남용 방지 (우선순위 Medium)

- 응답·화면에서 `paymentKey`, `idempotencyKey`, `guestId`, 내부 `id`가 빠지는지 정적·동적으로 확인(REQ-ORDER-039).
- 동일 출처 반복 실패 제한(REQ-ORDER-037) — 임계값과 창(window)은 M3 착수 시 결정하고 acceptance.md의 AC에 수치를 고정한다.

### M4 — 보존 검증 (우선순위 Low)

- `/checkout/complete/[orderId]`의 쿠키 진입 블록 diff가 0줄임을 확인.
- `findOrderForGuest()`와 주문 생성 트랜잭션 무변경 확인.
- 기존 테스트 전량 회귀 없음.
- 대응: REQ-ORDER-045.

## §5. 위험

| 위험 | 영향 | 완화 |
|---|---|---|
| `orderNumber`가 순차적이면 열거 공간이 좁아진다 | 주문 번호 추측이 쉬워져 대조값 하나에만 의존하게 됨 | M1 착수 시 생성 방식 확인. 순차적이면 별도 항목으로 올림 |
| 연락처는 지인이 알 수 있는 값이다 | 아는 사람이 주문을 열 수 있음 | 구조적으로 없앨 수 없음 — §6 잔여 위험으로 기록. 표시 항목에서 민감 정보를 빼는 것(REQ-ORDER-039)으로 피해를 줄인다 |
| 레이트 리밋의 저장소가 정해지지 않음 | M3 착수 시 배선 결정 필요 | 임계값·창·저장소를 M3에서 확정하고 AC에 수치로 고정 |
| 이행 상태값 요구가 나중에 되살아나면 범위가 커진다 | Tier M → L 재계획 | §0 결정 2로 범위 밖 확정(2026-09-03). 되살아나면 이 SPEC이 아니라 백로그 `t24`에서 다룬다 |

## §6. 잔여 위험 (없앨 수 없어 기록하는 것)

주문 번호와 수령인 연락처를 모두 아는 사람은 그 주문을 열 수 있다. 이는 채택한 대조 방식의 정의상 성질이며 이 SPEC이 제거하지 못한다. 표면적으로 낮추는 수단(구별 불가능한 실패, 반복 시도 제한, 민감 항목 미표시)은 REQ에 담았으나, "아는 사람"에 대한 방어는 아니다. 더 강한 보장이 필요하면 조회 전용 토큰(§1의 기각 대안 4)을 별도 SPEC으로 다시 검토한다.
