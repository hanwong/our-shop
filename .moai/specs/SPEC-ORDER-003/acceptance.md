# Acceptance Criteria: SPEC-ORDER-003 — 게스트 주문 재방문 조회와 주문 상태 표시

## §0. 검증 수단의 경계 (읽기 전에)

REQ 12건(REQ-ORDER-034 ~ 045)에 AC 13건(AC-ORDER-037 ~ 049)이 대응한다. **13:12인 이유**: REQ-ORDER-036(구별 불가능한 실패)은 서로 다른 두 관측을 요구한다 — 응답 본문·상태 코드가 같은가(AC-ORDER-039)와 실패 경로가 조회를 건너뛰어 빨라지지 않는가(AC-ORDER-040 — 응답 시간 절의 **구조적 대리 지표**이며 시간을 직접 재지 않는다, `AC-040-EXCL-TIMING`). 하나의 시나리오로 둘 다 판정할 수 없어 나눴다.

번호는 `ORDER` 도메인의 기존 번호를 이어받는다 — SPEC-ORDER-002가 AC-ORDER-036까지 사용했으므로 037부터 시작한다.

### 이름 붙은 제외 항목

- **`AC-041-EXCL-RATELIMIT` (M3 착수 시점 확정)**: 임계값·창(window)·저장소를 M3 착수 시 확정했다 — 동일 출처(IP) 기준 **60초 창에 5회 초과 시 429 + 15분 잠금**, 저장소는 인메모리 `Map`(`src/lib/auth/rate-limit.ts`의 `checkRateLimit()` 재사용). SPEC-AUTH-001이 REQ-AUTH-021에서 이미 세운 동일 정책을 그대로 재사용한 것이며 새 수치를 발명하지 않았다 — 코드 재사용 우선 원칙에 따른 선택이다. AC-ORDER-041은 이 수치로 판정한다.
- **`AC-040-EXCL-TIMING`**: REQ-ORDER-036은 실패 응답이 **응답 본문·상태 코드·응답 시간** 중 어느 것으로도 구별되지 않기를 요구한다. 이 SPEC의 자동 테스트는 그중 **응답 시간 채널을 직접 측정하지 않는다** — AC-ORDER-039가 본문과 상태 코드를 전수 비교로 판정하고, AC-ORDER-040은 시간 대신 **두 실패 경로의 저장소 조회 횟수가 같음**이라는 구조적 대리 지표로만 판정한다. 벽시계 시간은 부하에 따라 흔들려 재현되지 않기 때문이다. **이 대리 지표의 한계**: 조회 횟수가 같아도 인덱스 적중/미적중 차이 등으로 실측 지연 차이가 남을 수 있으므로, 조회 횟수 동일은 시간 구별 불가능성의 *증명*이 아니라 그 필요조건의 확인이다. 즉 REQ-ORDER-036의 응답 시간 절은 **이 SPEC의 자동 테스트로 검증되지 않는 항목**이며, 이 제외는 수치 확정을 기다리는 것이 아니라 영구적이다(닫히는 게이트 없음). 더 강한 보장이 필요해지면 별도 SPEC에서 시간 측정 수단을 세워 다룬다.

## §1. Given-When-Then 시나리오

### 조회 권한

**AC-ORDER-037** — 주문 번호와 연락처가 모두 일치할 때에만 주문이 열린다 (REQ-ORDER-034)
- Given: `orderNumber = "ORD-20260903-0001"`, `recipientPhone = "010-1234-5678"`인 주문이 하나 존재한다
- When: 그 주문 번호와 그 연락처로 조회한다
- Then: 그 주문의 내용이 반환되고, 반환된 주문의 `orderNumber`가 조회에 사용한 값과 같다.
- 검증 수단: fake DB + 서비스 단위 테스트.

**AC-ORDER-038** — 주문 번호만으로는 어떤 주문도 열리지 않는다 (REQ-ORDER-035)
- Given: 어떤 게스트 쿠키도 제시하지 않는 요청, 실재하는 주문 번호 하나, 그리고 그 주문의 것이 아닌 연락처 `"010-0000-0000"`
- When: 그 주문 번호와 틀린 연락처로 조회한다
- Then: 조회 결과가 비어 있고, 응답 본문에 주문 번호·상태·항목·금액·배송지 중 어떤 값도 담기지 않는다.
- 검증 수단: 응답 본문 전수 단언(주문 필드명이 하나도 등장하지 않음).

**AC-ORDER-039** — 없는 주문과 대조 실패가 응답으로 구별되지 않는다 (REQ-ORDER-036)
- Given: 어떤 게스트 쿠키도 제시하지 않는 요청, 실재하지 않는 주문 번호 `A`, 그리고 실재하지만 연락처가 틀린 주문 번호 `B`
- When: `A`로 조회한 응답과 `B`로 조회한 응답을 비교한다
- Then: 두 응답의 상태 코드가 같고 본문이 바이트 단위로 같다.
- 검증 수단: 두 응답 객체의 직접 비교 단언.

**AC-ORDER-040** — 실패 경로가 조회를 건너뛰어 빨라지지 않는다 (REQ-ORDER-036)
- Given: 어떤 게스트 쿠키도 제시하지 않는 요청, 실재하지 않는 주문 번호, 그리고 실재하지만 연락처가 틀린 주문 번호
- When: 두 경로를 각각 실행하며 저장소 조회 호출 횟수를 센다
- Then: 두 경로 모두 저장소 조회를 정확히 1회 수행한다(어느 쪽도 조회 없이 조기 반환하지 않는다).
- 검증 수단: fake 저장소의 호출 횟수 기록. **시간 측정이 아니라 호출 횟수로 판정한다** — 벽시계 시간은 부하에 따라 흔들려 재현되지 않기 때문이다.
- **시간 채널 미검증 — `AC-040-EXCL-TIMING`**: 이 AC는 REQ-ORDER-036의 "응답 시간" 절을 구조적 대리 지표로만 다루며 실제 시간을 측정하지 않는다. 제외의 범위와 대리 지표의 한계는 §0에 있다.

**AC-ORDER-041** — 반복 실패가 누적되면 대조를 수행하지 않는다 (REQ-ORDER-037)
- Given: 동일 출처(IP)에서 60초 이내 대조 실패가 5회 누적된 상태
- When: 같은 출처에서 한 번 더 조회를 시도한다
- Then: 요청이 429로 거부되고, 저장소 조회가 **호출되지 않는다**. 거부는 최초 초과 시점부터 15분간 유지된다.
- 검증 수단: fake 저장소의 호출 횟수 0 단언 + 429 응답 단언.
- **수치 확정 — `AC-041-EXCL-RATELIMIT`**: 임계값 5회 / 창 60초 / 잠금 15분, 저장소는 인메모리 `Map`(`checkRateLimit()` 재사용). 근거는 §0 참고.

### 조회 결과가 보여주는 것

**AC-ORDER-042** — 성공한 조회는 주문의 스냅샷 전부를 보여준다 (REQ-ORDER-038)
- Given: 항목 2건, 배송비와 할인이 모두 0이 아닌 주문 하나
- When: 올바른 주문 번호와 연락처로 조회 화면을 연다
- Then: 화면에 주문 번호, 주문 일시, 상태 문구, 두 항목의 상품명·단가·수량·줄 합계, 상품 합계·배송비·할인 금액·총액, 배송지의 수령인·연락처·우편번호·주소가 모두 나타난다.
- 검증 수단: 렌더링 결과에 대한 텍스트 단언.

**AC-ORDER-043** — 민감 항목과 내부 식별자는 노출되지 않는다 (REQ-ORDER-039)
- Given: `paymentKey`, `idempotencyKey`, `guestId`, 내부 `id`가 모두 채워진 주문
- When: 조회 화면을 열고 그 응답 본문과 렌더링 결과를 검사한다
- Then: 네 값 중 어느 것도 본문이나 화면에 등장하지 않는다.
- 검증 수단: 응답 본문·렌더링 문자열에 대한 부재 단언(값 자체를 검색).

**AC-ORDER-044** — 상태 표시는 저장된 값을 그대로 반영한다 (REQ-ORDER-040)
- Given: 상태가 각각 `pending_payment`, `paid`, `cancelled`인 주문 세 건
- When: 각각을 조회한다
- Then: 세 화면이 서로 다른 상태 문구를 보이고, 아래 **금지 문구 목록**의 어떤 문자열도 어느 화면에도 나타나지 않는다.
- 금지 문구 목록(닫힌 집합, 테스트에 상수로 고정한다): `배송 준비`, `상품 준비`, `준비 중`, `준비중`, `발송`, `출고`, `배송 중`, `배송중`, `배송 완료`, `배송완료`, `운송장`, `송장`. 저장된 `OrderStatus` 3종이 나타내지 않는 진행 단계를 뜻하는 문구를 열거한 것이며, 이 목록에 없는 문자열은 이 AC의 판정 대상이 아니다. 목록을 늘리려면 이 항목을 고쳐야 한다.
- 검증 수단: 렌더링 결과 텍스트 단언 + 위 목록 전수 부재 단언(목록을 순회하며 각 문자열의 부재를 확인).

**AC-ORDER-045** — 미결제 주문은 결제 전임을 알린다 (REQ-ORDER-041)
- Given: 상태가 `pending_payment`인 주문
- When: 조회 화면을 연다
- Then: 결제가 완료되지 않았음을 알리는 문구가 나타나고, 결제가 완료되었음을 뜻하는 문구는 나타나지 않는다.
- 검증 수단: 렌더링 결과 텍스트 단언.

### 진입 동선

**AC-ORDER-046** — 조회 입력 화면은 로그인 없이 열린다 (REQ-ORDER-042)
- Given: 어떤 인증 쿠키도 어떤 게스트 쿠키도 제시하지 않는 요청
- When: 조회 입력 경로를 연다
- Then: 주문 번호 입력란과 연락처 입력란을 가진 화면이 정상 렌더링되고, 로그인 화면으로 전환되지 않는다.
- 검증 수단: 렌더링 결과의 입력 요소 존재 단언.

**AC-ORDER-047** — 형식 검증 실패는 구체적으로 알리되 조회하지 않는다 (REQ-ORDER-043)
- Given: 주문 번호가 비어 있고 연락처 형식이 어긋난 입력
- When: 조회를 제출한다
- Then: 두 항목 각각에 대한 오류 문구가 나타나고, 저장소 조회가 호출되지 않는다.
- 검증 수단: 렌더링 결과 단언 + fake 저장소 호출 횟수 0 단언.

**AC-ORDER-048** — 귀속이 일치하는 게스트 쿠키는 대조 없이 연다 (REQ-ORDER-044)
- Given: 주문의 귀속 게스트 신원과 값이 같은 게스트 쿠키를 제시하는 요청
- When: 연락처를 제시하지 않고 그 주문의 조회 경로를 연다
- Then: 주문 내용이 표시된다. 같은 요청이 **다른 게스트의 주문**을 열려고 하면 표시되지 않는다.
- 검증 수단: 쿠키를 주입한 두 경우(일치/불일치)에 대한 렌더링 결과 단언.

**AC-ORDER-049** — 기존 완료 화면과 기존 조회 경로가 변경되지 않는다 (REQ-ORDER-045)

- Then: 세 대상 모두 diff가 0줄이고, 새 마이그레이션 파일이 생성되지 않았으며, 기존 테스트가 회귀 없이 전부 통과한다.

## §2. 엣지 케이스

| 상황 | 기대 동작 |
|---|---|
| 연락처 표기가 다름(`010-1234-5678` vs `01012345678`) | **범위 밖으로 확정 (M4, 2026-09-03 사용자 결정)** — 이 SPEC은 표기 정규화를 다루지 않는다. 근본 수정은 주문 생성 트랜잭션(REQ-ORDER-045가 보존을 요구하는 대상)을 건드려야 하므로 이 SPEC의 PRESERVE 범위와 충돌한다. 저장 시점(체크아웃 폼)이 형식을 검증하지 않고 자유 텍스트로 저장하는 반면 조회 측은 `RECIPIENT_PHONE_PATTERN`으로 형식을 제한하므로, 체크아웃 때 비표준 표기로 입력한 주문은 이 조회 기능으로 못 찾을 수 있는 잔여 위험이 있다. 후속 처리는 백로그 카드로 분리한다(§3 DoD 참고) |
| 같은 연락처로 주문이 여러 건 | 주문 번호가 유니크하므로 대조 결과는 항상 0건 또는 1건이다 |
| 주문 번호 대소문자 차이 | 정규화 후 대조. 규칙은 M1에서 고정 |

| 항목이 참조하던 상품이 삭제됨 | `OrderItem`은 상품명·단가 스냅샷을 자체 보유하고 FK가 `Restrict`이므로 표시에 영향이 없다 |
| 게스트 쿠키와 연락처를 함께 제시 | 어느 한쪽이라도 성립하면 연다(AC-ORDER-037, AC-ORDER-048) |
