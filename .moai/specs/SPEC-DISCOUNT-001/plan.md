# Plan: SPEC-DISCOUNT-001 — 쿠폰·할인 정책 계산 엔진 (게스트 주문)

## §0. 결정 기록

### 확정된 결정 — 조사로 모호성이 해소된 4건

아래 4건은 "결정이 필요해 보였으나 코드·스키마를 읽으면 실제로는 하나의 답만 성립하는" 항목이다. 근거를 함께 남긴다.

- **확정 — 할인은 `itemsSubtotal`에만 적용하고, 배송비는 건드리지 않는다.** `calculateShippingFee()`는 인자를 `void`로 버리고 항상 `0`을 반환한다(`order-service.ts:69-72`). 배송비가 상수 0이므로 "배송비 전/후"라는 구분은 **관측 가능한 차이를 만들지 못한다** — 두 선택지가 같은 숫자를 낸다. 따라서 이것은 열린 질문이 아니라 이미 답이 정해진 질문이다. 식은 `totalAmount = itemsSubtotal - discountAmount + shippingFee`로 고정한다(REQ-DISCOUNT-005). 배송비 정책이 실제로 생기는 시점에 그 SPEC이 "할인이 배송비에도 걸리는가"를 새로 정하면 된다.

- **확정 — 할인액은 품목별로 배분하지 않고 주문 단위 금액 하나로 표현한다.** `OrderItem.lineTotal`은 스키마 주석이 명시하듯 "나중에 산술이 바뀌어도 과거 주문의 숫자가 움직이지 않도록" 저장하는 **회계 기록**이다. 할인을 품목에 배분하면 `lineTotal`의 의미가 "상품 가격 × 수량"에서 "할인 반영 후 금액"으로 바뀌어, 이미 저장된 주문들과 의미가 갈라진다. 배분이 필요해지는 유일한 경우는 **부분 취소**인데, SPEC-PAYMENT-001의 취소는 주문 전체 단위이며(`markOrderCancelledAndRestoreStock()`이 주문의 모든 항목을 순회) 부분 취소 개념 자체가 없다. 필요를 만들지 않은 배분은 도입하지 않는다.

- **확정 — 무료배송 유형은 도입하지 않는다.** 위와 같은 근거다. 배송비가 상수 0인 저장소에서 무료배송 쿠폰은 산술적으로 아무 일도 하지 않는다. 있는 것처럼 만들면 **동작을 검증할 수 없는 기능**이 된다(할인 전후 금액이 동일하므로 성공과 실패를 구별하는 관측이 존재하지 않는다). spec.md §3에서 제외했다.

- **확정 — 관리자 쿠폰 저작은 범위 밖, 시드 스크립트로 대체한다.** 백로그에 `t11`("관리자 상품 등록/수정 백오피스")·`t12`("관리자 주문 목록·상태 변경 백오피스")가 queued로 존재한다. 또한 `Category` 모델은 주석에서 "미래의 admin SPEC이 데이터 변경만으로 카테고리를 추가·개명할 수 있도록" 테이블로 설계했다고 적고 있다 — **도메인 SPEC이 관리자 저작 기능을 떠안지 않는 선례**가 이 저장소에 이미 있다. 이 SPEC은 그 선례를 따른다. 검증에 필요한 쿠폰은 시드 스크립트(M1)가 만든다.

### 확정된 결정 — 새 모델은 정말로 필요한가 (단순성 사다리)

`moai-constitution.md` § Agent Core Behaviors 4의 단순성 사다리를 순서대로 적용한 결과를 남긴다. 결론은 **새 모델 1종이 필요하다**이다.

| 단계 | 검토 | 결과 |
|---|---|---|
| 1. 만들 필요가 있는가 | 카드 `t7`이 요구하는 기능이며, 쿠폰 코드를 담을 곳이 없으면 기능 자체가 성립하지 않는다 | 필요 |
| 2. 기존 구조 재사용 | `Category`(분류), `Product`(상품), `Cart`/`Order`(거래 기록) — 어느 것도 "코드·유효기간·사용상한"을 담는 의미가 아니다. 억지로 얹으면 모델의 의미가 무너진다 | 불가 |
| 3. 표준 라이브러리 / 4. 플랫폼 기능 | 할인 규칙은 애플리케이션 도메인 지식이며 언어·플랫폼이 제공하는 것이 아니다 | 해당 없음 |
| 5. 이미 설치된 의존성 | `package.json`에 규칙 엔진·프로모션 라이브러리가 없다. 정률/정액 두 유형에 외부 규칙 엔진을 들이는 것은 과잉이다 | 불필요 |
| 6. 한 줄로 가능한가 | 정률/정액 산술 자체는 몇 줄이지만, **코드의 지속·유효기간·사용 상한은 상태이며 저장소가 필요**하다 | 저장 필요 |
| 7. 최소 코드 | `Coupon` **1종**. 정책 테이블(`DiscountPolicy`)과 코드 테이블을 분리하는 2종 설계는 "하나의 정책이 여러 코드를 갖는" 요구가 생기기 전까지 아무것도 벌지 못한다 | **Coupon 1종** |

별도 `CouponRedemption`(사용 이력) 테이블도 검토했으나 도입하지 않는다: 주문↔쿠폰 연결은 `Order.couponCode` 스냅샷으로 충분하고, 상한 강제는 `Coupon.redeemedCount` 카운터의 조건부 원자 갱신으로 충분하다. 이력 테이블은 인별 제한이나 사용 분석이 필요해질 때 값을 갖는데, 전자는 강제 불가(spec.md §3)이고 후자는 이 SPEC의 목적이 아니다.

### 확정된 결정 — 사용자 결정으로 해소된 4건 (2026-09-02)

아래 4건은 코드·스키마·백로그를 모두 읽고도 **하나의 답으로 좁혀지지 않아** 명확화 대기 항목으로 남겨 두었던 것이다. **2026-09-02 사용자 결정으로 4건 모두 확정**되었고, 네 건 모두 잠정 권고와 같은 (A)로 정해졌다. 대기 마커는 제거했으며 run-phase 진입을 막는 열린 항목은 이제 없다.

각 항목에 결정과 함께 **받아들인 트레이드오프**를 남긴다. 무엇을 골랐는지만 적고 무엇을 포기했는지 적지 않으면, 나중에 그 대가를 만난 사람이 그것을 결정이 아니라 실수로 읽는다.

**확정 #1 — 쿠폰 입력 UI는 이 SPEC이 최소한으로 만든다 (선택지 A, 2026-09-02 사용자 결정)**

- **무엇이 걸려 있나**: `/checkout` 화면은 **이미 존재한다**(`src/app/checkout/page.tsx` + `CheckoutForm` + `OrderSummary`). 따라서 "UI가 들어갈 자리가 없다"는 제약은 성립하지 않는다 — 자리는 있다. 문제는 **소유권**이다: 백로그 카드 `t10`("장바구니·체크아웃 화면 UI")이 이 화면의 UI를 별도로 다루기로 되어 있다.
- **선택지 (A)**: 이 SPEC이 **최소한의 입력란 + 실패 문구**만 만든다. 스타일링·레이아웃·상호작용 개선은 `t10`이 가져간다.
- **선택지 (B)**: 이 SPEC은 **엔진과 API까지만** 만들고 화면은 전혀 건드리지 않는다. 입력란은 `t10`이 만든다.
- **트레이드오프**: (B)는 경계가 깨끗하지만 **완성 시점에 기능이 도달 불가능**해진다 — 코드를 입력할 곳이 없으므로 엔진이 실제 주문 경로에서 한 번도 실행되지 않고, 단위 테스트 밖에서는 검증할 수단이 없다. `t10`이 언제 착륙할지 알 수 없는 상태에서 이는 "동작한다고 주장하지만 아무도 써본 적 없는" 코드를 남긴다. (A)는 `t10`과 파일이 겹칠 위험이 있으나, 겹치는 범위가 입력란 하나로 작고 `t10`이 나중에 착륙하므로 그쪽이 흡수하면 된다.
- **확정**: **(A)** — 이 SPEC이 **코드 입력란과 실패 문구 표시까지만** 만든다. 검증 가능성이 경계의 깔끔함보다 무겁다는 판단이다. 이 SPEC의 UI 요구사항은 "최소한"으로 한정되며, 스타일링·레이아웃·상호작용 개선은 만들지 않는다.
- **경계 기록 — `t10`이 같은 컴포넌트를 다시 건드리는 이유**: 백로그 카드 `t10`("장바구니·체크아웃 화면 UI")은 이 SPEC이 만든 입력란을 **재작업(restyle)하는 것이 정상 경로**다. 중복 작업이 아니라 합의된 분업이다 — 이 SPEC은 기능이 도달 가능한 상태를 만드는 데까지만 책임지고, 그 화면의 시각적 완성도는 `t10`이 소유한다. 나중에 `t10`을 집는 사람은 이 컴포넌트를 "이미 누가 만들었는데 왜 또 손대나"로 읽지 말고, **처음부터 그렇게 나눈 것**으로 읽어야 한다.
- **받아들인 대가**: 같은 파일을 두 카드가 순차로 건드린다. 겹치는 범위가 입력란 하나로 작고 `t10`이 나중에 착륙하므로 그쪽이 흡수한다.

**확정 #2 — 전역 총량 상한만 두고, 인별 제한은 제공하지 않는다 (선택지 A, 2026-09-02 사용자 결정)**

- **무엇이 걸려 있나**: 쿠폰의 사용 남용을 어디까지 막을 것인가. 조사로 확인한 제약은 단단하다 — `Order`의 유일한 신원은 `guestId`이고 그 값은 쿠키에서 온다(`Order.guestId` NOT NULL, `userId` 컬럼 자체가 없음). **쿠키를 지우면 새 사람이 된다.** 회원 신원은 SPEC-ORDER-001이 구조적으로 제외했다.
- **선택지 (A)**: **전역 총량 상한만** 둔다(`maxRedemptions`). "이 코드는 통틀어 100번까지". 인별 제한은 제공하지 않으며 **제공한다고 주장하지도 않는다**.
- **선택지 (B)**: `guestId` 기준 사용 이력을 남겨 "이 게스트는 이미 썼다"를 막는다.
- **선택지 (C)**: 쿠폰 기능 자체를 회원에게만 허용한다.
- **트레이드오프**: (B)는 **막는 것처럼 보이지만 실제로는 막지 못한다** — 쿠키 삭제 한 번으로 우회되므로, 우회 비용이 거의 0인 방어를 위해 테이블과 코드를 늘리는 셈이다. 더 나쁜 것은 그것이 "인별 제한이 있다"는 **잘못된 안심**을 만든다는 점이다. (C)는 회원 체크아웃이 이 저장소에 **존재하지 않으므로** 기능을 0명에게 제공하는 것과 같다.
- **확정**: **(A)** — `maxRedemptions` **전역 총량 상한 하나만** 둔다. 강제할 수 있는 것만 강제하고, 강제할 수 없는 것은 없다고 명시한다(REQ-DISCOUNT-022).
- **받아들인 한계 — 이것은 조용한 공백이 아니라 명시된 한계다**: 한 사람이 쿠키를 지우고 같은 쿠폰을 여러 번 쓰는 것을 **이 SPEC은 막지 못한다**. 막지 못한다는 사실 자체를 산출물에 적는 것이 이 결정의 절반이다 — REQ-DISCOUNT-022가 "인별 제한이 있다"는 주장 자체를 금지하고, AC-DISCOUNT-022가 그 부재를 검색으로 검증한다. `maxRedemptions`를 설명하는 자리마다 전역 상한임을 함께 적는다.
- **언제 다시 열리나**: 인별 제한이 사업적으로 필요해지면, 그것은 회원 체크아웃(카드 `t18`이 추적하는 서버 렌더 신원 문제)이 해결된 뒤의 SPEC이다. 신원이 없는 채로 인별 제한을 만드는 것은 방어가 아니라 잘못된 안심이다.

**확정 #3 — 정률·정액 두 유형을 모두 지원하고, 정률은 원 단위 내림한다 (선택지 A, 2026-09-02 사용자 결정)**

- **무엇이 걸려 있나**: 첫 판에 몇 가지 유형을 담을 것인가. 무료배송은 제외가 확정되었고(§0), 남은 후보는 정률(`PERCENTAGE`)과 정액(`FIXED_AMOUNT`)이다.
- **선택지 (A)**: 두 유형 모두 지원. 유형 열거형 + 값 컬럼 하나로 표현.
- **선택지 (B)**: 정액 하나만. 반올림 규칙이 아예 필요 없어져 가장 단순하다.
- **선택지 (C)**: 정률 하나만. 실무에서 더 흔하지만 원 단위 내림 규칙을 반드시 정해야 한다.
- **트레이드오프**: (A)의 추가 비용은 **작다** — 열거형 한 개와 계산 분기 한 줄이며, 데이터 모델은 (B)/(C)와 동일하다. 반면 (B)나 (C)로 시작하면 나머지 하나를 추가할 때 **마이그레이션과 저장된 쿠폰의 의미 재해석**이 필요하다(값 컬럼이 "원"인지 "%"인지 바뀌므로). 다만 (A)는 정률의 **내림 규칙**(REQ-DISCOUNT-007)이라는 되돌리기 어려운 결정을 지금 확정하게 만든다 — 이미 저장된 주문 금액은 나중에 규칙이 바뀌어도 움직일 수 없기 때문이다.
- **확정**: **(A)** — `PERCENTAGE`와 `FIXED_AMOUNT` 두 유형을 모두 지원하며(REQ-DISCOUNT-003), 정률은 **원 단위 내림(`floor`)**으로 고정한다(REQ-DISCOUNT-007, AC-DISCOUNT-007이 `33333 × 10% → 3333` 경계값으로 못박는다).
- **내림을 고른 이유**: 올림·반올림은 **고객에게 불리한 방향으로 1원이 어긋날 수 있는** 반면 내림은 항상 고객에게 유리하거나 같다. 금액 분쟁이 생길 때 그 방향이 한쪽으로 고정되어 있는 편이 안전하다.
- **되돌리기 어려움을 인정한다**: 이 방향은 **저장된 주문 금액을 통해 영구화**된다. 나중에 규칙을 뒤집어도 이미 저장된 주문의 숫자는 움직일 수 없으므로, 그 시점부터 과거 주문과 새 계산이 1원 어긋난다. 지금 확정하는 것이 이 결정의 목적이다(§6 리스크 표).

**확정 #4 — 주문 생성 시점에 증가하고 취소 웹훅에서 해제한다 (선택지 A, 2026-09-02 사용자 결정)**

- **무엇이 걸려 있나**: 쿠폰 사용 횟수를 **주문 생성 시점**에 올린다면(재고 차감과 같은 시점 — SPEC-ORDER-001이 확정한 타이밍), 결제하지 않고 이탈한 주문이 쿠폰 한 장을 **영구히 점유**한다. 취소 웹훅이 도달하는 경로는 되돌릴 자리가 이미 있지만(`payment-repository.ts:135-140`의 재고 복원 트랜잭션), **아무 일도 일어나지 않은 채 방치된 주문**은 그 경로를 타지 않는다.
- **이것은 새로운 문제가 아니다**: 백로그 카드 `t21`이 **재고에 대해 정확히 같은 공백**을 추적하고 있다("결제 안 한 주문(pending_payment)의 재고 점유를 시간 경과로 해제하는 소유자 없음"). SPEC-ORDER-002는 이를 범위 밖으로 두고 `t21`에 넘겼다.
- **선택지 (A)**: 선례를 따른다 — 생성 시점에 증가, 취소 웹훅 경로에서 해제(REQ-DISCOUNT-021), 시간 기반 해제는 범위 밖으로 두고 **`t21`에 쿠폰 축을 덧붙이거나 새 카드를 세운다**.
- **선택지 (B)**: 증가 시점을 **결제 승인 시점**으로 미룬다. 이탈 주문이 쿠폰을 점유하지 않는다.
- **트레이드오프**: (B)는 이탈 문제를 없애지만 **새 문제를 만든다** — 주문 생성 시 상한을 확인해 놓고 결제 시점에 다시 확인해야 하므로, 그 사이에 쿠폰이 소진되면 **이미 배송 정보를 입력하고 결제까지 마친 고객이 거절**된다. 재고는 이미 (A) 방식으로 결정되어 있으므로 (B)는 같은 트랜잭션 안에서 **두 자원이 서로 다른 시점 규칙**을 갖게 만든다 — 추론하기 어렵고, 두 규칙의 교차 실패 조합을 새로 설계해야 한다.
- **확정**: **(A)** — 사용 횟수는 **주문 생성 트랜잭션 안에서** 증가하고(REQ-DISCOUNT-015·016, design.md §3.1의 3f), **결제 취소 웹훅이 재고를 복원하는 같은 트랜잭션에서** 해제한다(REQ-DISCOUNT-021). 재고와 같은 시점 규칙을 쓰는 것이 일관성과 추론 가능성 모두에서 낫다.
- **받아들인 공백 — 시간 기반 해제는 소유자가 없다**: 결제도 취소도 하지 않고 방치된 `pending_payment` 주문은 취소 웹훅 경로를 타지 않으므로, 그 주문이 점유한 쿠폰 사용분은 **되돌아오지 않는다**. 이탈 주문 수만큼 유효 쿠폰이 조기 소진된다. 이 SPEC은 이를 인수하지 않고 기록만 한다(spec.md §3).
- **이 공백의 소유자 — 아직 없다**: 구조적으로 카드 `t21`("결제 안 한 주문의 재고 점유를 시간 경과로 해제하는 소유자 없음")과 **완전히 같은 성격의 공백**이다. 트리거가 시간인 작업은 스케줄러라는 새 실행 축을 요구하며, 그 축은 이 저장소에 아직 없다. **다만 쿠폰 축을 위한 백로그 카드는 아직 만들어지지 않았다** — `t21`에 쿠폰 축을 덧붙일지 별도 카드를 세울지는 정해지지 않았고, 여기서 존재하지 않는 카드 번호를 인용하지 않는다. 재고 축의 해법이 정해질 때 쿠폰 축도 같은 자리에서 함께 다루는 것이 자연스럽다.

## §1. 핵심 설계 결정 — 할인을 어디에 두는가 (되돌리기 가장 어려운 결정)

**결정: 할인은 `Order.totalAmount`에 미리 녹여 넣는다.** 즉 `totalAmount`는 여전히 "고객이 실제로 낼 금액"이며, 할인은 그 값을 만드는 과정에 참여하되 결과 뒤에 따로 붙지 않는다.

이 결정이 되돌리기 가장 어려운 이유는 **결제 경로가 이미 `totalAmount`에 의존하고 있기 때문**이다. `payment-service.ts:83`의 `if (order.totalAmount !== amount)`는 어떤 Toss 호출보다 먼저 실행되는 유일한 금액 관문이다. 세 가지 대안을 검토했다.

| 안 | 내용 | 판정 |
|---|---|---|
| **A. totalAmount에 녹인다** | `totalAmount = itemsSubtotal - discountAmount + shippingFee`. `discountAmount`는 별도 컬럼으로 **기록**되지만 금액 계산의 결과에는 이미 반영됨 | **채택** |
| B. totalAmount는 할인 전, 결제 시 차감 | `totalAmount`는 정가, 결제 요청 시 할인 적용 | 기각 — `payment-service.ts:83`의 대조 대상이 달라져 **결제 검사 로직을 고쳐야** 한다. 금액 검사는 이 저장소에서 가장 보안 민감한 코드이며(승인 리다이렉트 경로의 REQ-PAYMENT-006이 순서까지 고정), 할인 기능을 위해 그것을 건드리는 것은 위험 대비 이득이 없다 |
| C. 별도 `finalAmount` 컬럼 신설 | `totalAmount`는 그대로 두고 결제는 `finalAmount`를 본다 | 기각 — "진짜 금액"이 두 개가 되어, 이후 모든 코드가 **어느 쪽을 봐야 하는지** 매번 판단해야 한다. 잘못 고른 한 곳이 곧 결제 사고다 |

**A안의 결과로 바뀌지 않는 것들** — 이것이 A안의 값어치다:

- `payment-service.ts`: 한 줄도 바뀌지 않는다(REQ-DISCOUNT-020).
- `confirmTossPayment` 호출과 웹훅 처리: 바뀌지 않는다.
- `OrderItem.lineTotal` / `itemsSubtotal`: 바뀌지 않는다(REQ-DISCOUNT-006).
- 쿠폰 없는 주문: 금액도 응답 형태도 이전과 동일(REQ-DISCOUNT-019).

**바뀌는 것은 두 곳뿐이다**: `order-service.ts`의 금액 계산 3단계(할인 산출 + 사용 횟수 증가), 그리고 `/checkout`이 화면에 표시하고 `confirmedTotal`로 실어 보내는 값.

## §2. 데이터 모델

`Coupon` 1종을 추가하고, `Order`에 스냅샷 컬럼 2개를 더한다.

```
model Coupon
  id             String     @id @default(cuid())
  code           String     @unique   // 대문자 정규화 저장 (REQ-DISCOUNT-002)
  type           DiscountType         // PERCENTAGE | FIXED_AMOUNT
  value          Int                  // 정률이면 퍼센트, 정액이면 원 (REQ-DISCOUNT-003)
  minOrderAmount Int        @default(0)
  maxRedemptions Int                  // 전역 상한 (REQ-DISCOUNT-022 — 인별 아님)
  redeemedCount  Int        @default(0)
  startsAt       DateTime
  endsAt         DateTime
  createdAt / updatedAt

enum DiscountType { PERCENTAGE  FIXED_AMOUNT }
```

`Order`에 추가하는 컬럼 — 둘 다 **스냅샷**이며 `Coupon`으로의 외래키가 아니다:

```
  couponCode     String?    // 적용된 코드의 사본. 쿠폰이 지워져도 주문은 남는다
  discountAmount Int  @default(0)   // 적용 시점에 확정된 할인액
```

**외래키를 두지 않는 이유**가 이 절의 핵심이다. `OrderItem`이 `productName`·`unitPrice`를 **조인하지 않고 복사해 저장**하는 것과 같은 이유다(스키마 주석: "조인하면 현재 값이 나오는데, 주문에는 고객이 동의한 값이 필요하다"). 쿠폰도 마찬가지로 나중에 값이 바뀌거나 폐기될 수 있으며, 그때 과거 주문의 할인액이 따라 움직이면 회계 기록이 무너진다. `@default(0)`은 기존 주문 행들이 마이그레이션 후에도 유효하게 만든다(REQ-DISCOUNT-019).

## §3. 동시성 — 사용 상한은 새로 발명하지 않는다

마지막 한 장의 쿠폰을 두 주문이 동시에 요청하는 문제는 SPEC-ORDER-002가 재고에서 이미 푼 문제와 **같은 모양**이다. 그 전략을 차용한다(`order-repository.ts:129-139`).

- 조건부 원자 갱신: `updateMany({ where: { id, redeemedCount: { lt: maxRedemptions } }, data: { redeemedCount: { increment: 1 } } })`.
- 영향 행 수가 1이 아니면 경쟁에서 진 것이며 `COUPON_EXHAUSTED`로 거절한다(REQ-DISCOUNT-017).
- 주문 생성 트랜잭션 **안에서** 수행하므로 롤백이 증가분을 함께 되돌린다(REQ-DISCOUNT-015).

**교착 순서에 대한 관찰**: SPEC-ORDER-002 REQ-ORDER-023은 재고 차감을 상품 id 오름차순으로 수행해 교착을 피한다. 쿠폰은 주문당 **한 행**만 갱신하므로 그 자체로는 순서 문제를 만들지 않으나, 재고 루프와 쿠폰 갱신의 **상대 순서**는 고정되어야 한다. 설계는 design.md §3에서 다룬다.

## §4. 마일스톤 (우선순위 기반, 되돌리기 어려운 것부터)

| M | 이름 | 내용 | 우선순위 |
|---|---|---|---|
| **M1** | 데이터 모델과 마이그레이션 | `Coupon` 모델 + `DiscountType` enum + `Order` 컬럼 2개, 마이그레이션, 검증용 시드 스크립트 | High |
| **M2** | 순수 계산 엔진 | 유형별 할인액 산출, 내림 규칙, 상한 클램프. DB·시계 접근 없음 (REQ-DISCOUNT-004~008) | High |
| **M3** | 쿠폰 검증 서비스와 실패 코드 | 조회·유효기간·최소금액·소진 검사, 4종 실패 코드 (REQ-DISCOUNT-009~013) | High |
| **M4** | 주문 트랜잭션 통합 | 금액 식 변경, `confirmedTotal` 대조, 조건부 원자 갱신, 스냅샷 저장 (REQ-DISCOUNT-014~019) | High |
| **M5** | 결제 취소 시 사용분 해제 | 기존 취소 트랜잭션에 쿠폰 되돌리기 추가 (REQ-DISCOUNT-021) | Medium |
| **M6** | 사전 검증 엔드포인트 + 체크아웃 최소 UI | **(a) `POST /api/discounts/validate`** — 코드와 `itemsSubtotal`을 받아 할인액 또는 거절 사유를 돌려주는 **무쓰기** 엔드포인트. 사용분을 점유하지 않으며 강제도 아니다 (REQ-DISCOUNT-025, design.md §5). **(b) 화면** — 코드 입력란 + 적용 결과 표시 영역 + 4종 거절 문구 + 금액 요약의 할인 행 (REQ-DISCOUNT-023·024). **§0 확정 #1에 따라 "최소한"으로 한정**되며 스타일링은 `t10`이 가져간다 | Medium |
| **M7** | 회귀 방어와 정직성 검증 | 쿠폰 없는 경로의 무변화 확인, 인별 제한 미주장 확인 (REQ-DISCOUNT-019, 022) | Medium |

M1~M7 전부 확정된 범위다. §0 확정 #1이 (A)로 정해졌으므로 **M6는 유지**되며, 그 범위는 사전 검증 엔드포인트·코드 입력란·적용 결과 표시 영역·4종 거절 문구·금액 요약의 할인 행까지로 한정된다.

**(a)와 (b)가 한 마일스톤인 이유**: 화면이 코드 적용 결과를 보여주려면 주문 제출과 별개의 왕복이 필요하고(design.md §5), 그 왕복의 상대가 이 엔드포인트다. 둘은 같은 사용자 동작 하나를 성립시키므로 함께 착륙해야 한다. M6 안에서는 (a)가 (b)보다 앞선다 — 엔드포인트 없이 UI를 먼저 만들면 UI가 자기 검증 경로를 임시로 만들었다가 버리게 된다.

**M6(a)의 남용 표면은 이 SPEC이 닫지 않는다**: 검증 엔드포인트는 코드의 존재 여부를 알려주므로 코드 추측(열거)에 쓰일 수 있다. 이 SPEC은 속도 제한을 도입하지 않으며, 그 사실을 design.md §5와 research.md §5에 관찰로 남긴다 — 없는 방어를 있다고 하지 않기 위함이다. REQ-DISCOUNT-025는 이 엔드포인트의 **무쓰기 성질**만을 요구하며, 남용 방어를 요구하지 않는다. 위험을 정직하게 기록한 것과 그 표면을 만들 권한을 부여하는 것은 다른 일이므로, 권한은 REQ-DISCOUNT-025가 명시적으로 부여한다.

## §5. 보존해야 할 것 (PRESERVE)

run-phase가 **깨뜨리면 안 되는** 기존 계약이다.

- `payment-service.ts`의 금액 검사와 그 **실행 순서**(어떤 Toss 호출보다 먼저). 이 SPEC은 이 파일을 변경 대상으로 삼지 않는다.
- `OrderItem.lineTotal` = `unitPrice × quantity`. 할인은 여기에 스며들지 않는다.
- `PRICE_CHANGED`의 의미("서버 계산과 고객이 본 금액이 다르다"). 대조 **대상**만 할인 후 금액으로 바뀌고 의미는 그대로다.
- 멱등키 재생 경로와 그 소유자 검사(`replayed.guestId === guestId`).
- SPEC-ORDER-002가 고정한 재고 차감의 상품 id 오름차순 순서.
- 쿠폰을 쓰지 않는 모든 주문의 동작 — 금액, 응답 형태, 실패 코드 전부.
