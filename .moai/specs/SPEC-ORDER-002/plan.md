# Plan: SPEC-ORDER-002 — 재고 차감 동시성 제어와 품절 처리

## §0. 결정 기록과 미해결 질문

### 확정 — 동시성 전략은 새로 고르지 않는다

조사 결과 `order-repository.ts:134-138`에 이미 조건부 원자 갱신이 있다. 이 SPEC은 그것을 **채택하고 계약으로 고정**하며(REQ-ORDER-022), 그 위에 순서·보고·검증을 얹는다. 대안 검토와 기각 사유는 §1에 있다.

### 확정된 결정 — run-phase 진입 전에 확정해야 했던 2건 (2026-09-02 사용자 확정)

- **확정 — CI DB 배선 소유권은 (B).** REQ-ORDER-032의 동시성 하네스는 살아 있는 PostgreSQL을 요구한다. 이를 CI 필수 검사로 만들려면 `.github/workflows/ci.yml`에 `services: postgres`와 마이그레이션 단계를 추가해야 하는데, 그 파일은 SPEC-CI-001이 소유한다. **확정된 선택은 (B)** — 하네스는 이 SPEC(M4)이 만들되 `DATABASE_URL` 도달 가능 여부로 게이트하고(도달 불가면 건너뛴 사실을 남기며 통과), CI 필수 검사로의 **승격은 SPEC-CI-001이 소유하는 후속 SPEC으로 명시적으로 미룬다**. REQ-ORDER-032를 `Where`(능력 게이트) 형태로 쓴 이유가 그것이며, 아래 설계는 (B)를 전제한다. **받아들인 공백**: (B)를 택했으므로 이 SPEC이 닫으려던 `AC-013-EXCL-CONCURRENCY`는 **개발자 기계에서만** 닫히고, 후속 CI SPEC이 착륙하기 전까지 CI에서는 열린 채로 남는다. 이것은 사용자가 확인하고 받아들인 공백이지 누락이 아니다 — 그리고 REQ-ORDER-033에 따라 어떤 산출물도 이 공백을 닫힌 것처럼 제시하지 않는다.

- **확정 — 미결제 주문 재고 해제는 이 SPEC의 범위 밖, 백로그 카드 `t21`이 이어받는다.** spec.md §3 첫 항목이 기록한 대로, 시간 기반 재고 해제는 SPEC-ORDER-001과 SPEC-PAYMENT-001 사이에서 **인수되지 않은 채 남아 있다**. 재고를 차감해 두고 되돌릴 경로가 결제 취소 웹훅 하나뿐이라는 사실은 이 SPEC이 굳히는 동시성 보증의 실효를 제한한다(결제하지 않고 이탈한 주문만큼 재고가 영구히 잠긴다). **확정된 선택은 범위를 넓히지 않는 것** — 이 SPEC은 그 사실을 기록만 하고 인수하지 않는다. 대신 별도 백로그 카드 **`t21`**("결제 안 한 주문(pending_payment)의 재고 점유를 시간 경과로 해제하는 소유자 없음 — SPEC-ORDER-001·SPEC-PAYMENT-001 사이에서 인수되지 않음")을 세워 추적한다. 즉 이 구조적 제약은 사라진 것이 아니라, 이 SPEC 밖에서 `t21`이 소유자를 찾는다.

## §1. 핵심 설계 결정 — 동시성 전략 (되돌리기 가장 어려운 결정)

### 채택: 조건부 원자 갱신 (이미 있는 것)

```ts
tx.product.updateMany({
  where: { id: productId, stock: { gte: quantity } },
  data:  { stock: { decrement: quantity } },
});   // count === 1 이면 성립, 0 이면 재고 부족
```

PostgreSQL의 UPDATE는 대상 행에 배타 잠금을 잡고, 잠금을 기다렸다가 획득한 뒤 **조건을 다시 평가**한다(Read Committed의 EvaluatePlanQual). 그래서 두 트랜잭션이 같은 행을 노리면 뒤에 온 쪽은 앞의 커밋 결과를 보고 조건을 재평가하며, 재고가 모자라면 `count === 0`을 받는다. 애플리케이션이 읽고 비교하는 구간이 없으므로 경쟁 구간 자체가 존재하지 않는다.

### 기각한 대안과 사유

| 대안 | 기각 사유 |
|---|---|
| `SELECT ... FOR UPDATE` 후 갱신 | Prisma에 이를 표현하는 일급 API가 없어 `$queryRaw`로 내려가야 한다. 질의 계층이 두 갈래로 갈라지는 대가를 치르면서 얻는 것은 **같은 행 잠금**이다 — 조건부 UPDATE가 이미 그 잠금을 잡는다. 대가만 있고 이득이 없다 |
| 트랜잭션 격리 수준을 `Serializable`로 상향 | 직렬화 실패(40001)가 **정상 경로에서도** 발생하므로 모든 주문에 재시도 루프를 달아야 한다. 상품 한 행을 조건부로 갱신하는 이 패턴에서는 Read Committed + 조건부 UPDATE가 이미 동일한 정확성을 주므로, 재시도 기계를 새로 들이는 비용이 정당화되지 않는다 |
| 유니크 제약 충돌로 경쟁 탐지 | 재고는 **카운터**이지 유일성의 대상이 아니다. 유니크 제약을 걸 열이 없다. (같은 기법이 이 저장소에서 이미 쓰이는 곳은 `Order.idempotencyKey`이며, 그것은 유일성이 실제 도메인 규칙인 경우다) |
| 재고 예약(hold) 행 + TTL | 스키마에 예약 개념이 없고(`Product.stock` 정수 한 개), TTL은 스케줄러라는 새 실행 축을 요구한다. spec.md §3에서 제외 |
| 분산 락(Redis 등) | 의존성이 없고, 단일 데이터베이스에서 행 잠금으로 해결되는 문제에 외부 조정자를 들이는 것은 과설계다 |

### 이 전략이 성립하려면 추가로 필요한 것 (= 이 SPEC의 실체)

조건부 갱신은 **한 행**에 대해서는 완전하다. 문제는 그 바깥에 있다.

1. **여러 행을 잠글 때의 순서** — 순서가 다르면 교착한다(G1). → 상품 id 오름차순 고정(REQ-ORDER-023).
2. **실패했을 때 무엇을 보고하는가** — 트랜잭션 시작 시점의 스냅샷 값을 보고하면 거짓말이 된다(G2), 첫 실패에서 멈추면 절반만 말한다(G3). → 실패 후 같은 트랜잭션에서 재조회하고 전량 보고(REQ-ORDER-025/026).
3. **교착을 만났을 때 무엇을 반환하는가** — 지금은 미분류 500이다. → 재시도 가능으로 식별(REQ-ORDER-027).
4. **성립을 관측했는가** — 아직 없다. → 실 DB 하네스(REQ-ORDER-032).

**자동 재시도 루프는 만들지 않는다.** REQ-ORDER-023은 이 SPEC이 다루는 **차감 경로 안**에서의 교착 원인(순서 불일치)을 제거한다 — 복원 경로(`payment-repository.ts` `markOrderCancelledAndRestoreStock()`)는 순서 규칙 밖에 있어(§5 PRESERVE, 관찰 사항으로만 기록) 차감과의 교착이 이론상 남을 수 있으나, 그 경우도 REQ-ORDER-027이 `CONCURRENCY_RETRY` 409로 흡수한다. 교착이 남아 관측된다면 그때 원인을 다시 진단한다 — 재시도로 덮으면 원인이 보이지 않게 된다.

## §2. 계약 변경 — 실패 응답의 형태

타입은 이미 복수를 약속한다(`InsufficientStockProduct[]`). 변경되는 것은 **채워지는 내용**이지 형태가 아니다.

| 필드 | 지금 | 이 SPEC 이후 |
|---|---|---|
| `products` | 첫 실패 항목 1건 | 재고가 요청 수량보다 적은 **모든** 항목 |
| `products[].available` | 트랜잭션 시작 시점의 스냅샷 값 | 차감 실패 직후 같은 트랜잭션에서 재조회한 값 |

새 실패 코드 1건을 추가한다.

| 코드 | 상태 | 의미 |
|---|---|---|
| `CONCURRENCY_RETRY` | 409 | 데이터베이스가 교착·직렬화 실패로 트랜잭션을 중단시켰다. 아무것도 반영되지 않았으며 그대로 다시 제출할 수 있다 |

`OrderFailureCode` 유니온과 `SubmitFailure` 인터페이스가 함께 넓어진다. 기존 4개 코드(`CART_EMPTY`/`PRICE_CHANGED`/`INSUFFICIENT_STOCK`/회원 거부)의 의미는 바뀌지 않는다.

## §3. 화면 흐름 (사용자가 실제로 보는 것)

### 주문서 진입 시점 — 알리되 막지 않는다

`OrderSummary`가 항목마다 `CartItemDTO.stock`과 `quantity`를 비교해 세 상태 중 하나를 표시한다: 정상(표시 없음) / `재고 부족 — 현재 N개` / `품절`. 새로 조회하지 않는다 — 이미 받고 있는 값이다.

제출 버튼은 **비활성화하지 않는다**(REQ-ORDER-029). 화면이 읽은 재고는 렌더 시점의 값이고, 렌더와 제출 사이에 재입고가 있을 수 있다. 화면이 막으면 그 사이 다시 살 수 있게 된 주문자가 이유 없이 막힌다. 판정의 권위는 트랜잭션 하나뿐이라는 원칙을 화면에서도 지킨다.

### 경쟁에서 진 순간 — 무엇이 왜 안 되었는지

`CheckoutForm`이 `INSUFFICIENT_STOCK` 응답의 `products`를 항목 목록으로 렌더한다. `PRICE_CHANGED`가 이미 새 금액을 화면으로 끌어올리는 선례를 그대로 따른다 — 주문자가 바로 조치할 수 있는 정보는 응답 본문에 묻어두지 않는다.

`CONCURRENCY_RETRY`는 목록 없이 "다시 시도해 주세요" 계열의 문구로 표시한다. 이 경우 부족한 상품이 특정되지 않았기 때문이며, 상품을 특정한 척하지 않는 것이 중요하다.

## §4. 마일스톤 (우선순위 순)

### M1 — 실패 보고의 정확성 (우선순위 High)
- `order-repository.ts`: 주어진 상품 id 집합의 현재 재고를 읽는 조회 함수 추가(트랜잭션 클라이언트 필수).
- `order-service.ts`: 차감 실패 시 재조회 → 요청 수량보다 적은 모든 항목을 `products`에 담아 abort.
- 대응: REQ-ORDER-025, REQ-ORDER-026.

### M2 — 결정적 차감 순서와 중단 매핑 (우선순위 High)
- `order-service.ts`: 차감 루프 진입 전 상품 id 오름차순 정렬. 정렬은 **차감 순서에만** 적용하고, 주문 항목의 저장·표시 순서(`createdAt` 기준)는 건드리지 않는다 — 완료 화면의 항목 순서가 바뀌면 SPEC-ORDER-001 `ORDER_INCLUDE`의 의도를 깨뜨린다.
- 교착·직렬화 실패(PostgreSQL 40P01/40001, Prisma `P2034` 경유)를 `CONCURRENCY_RETRY`로 매핑.
- 대응: REQ-ORDER-022, REQ-ORDER-023, REQ-ORDER-027.

### M3 — 주문서 화면의 재고 표면화 (우선순위 Medium)
- `OrderSummary.tsx`: 항목별 재고 부족/품절 표시.
- `CheckoutForm.tsx`: `products` 목록 렌더, `CONCURRENCY_RETRY` 문구.
- 대응: REQ-ORDER-028, REQ-ORDER-029, REQ-ORDER-030.

### M4 — 실 PostgreSQL 동시성 하네스 (우선순위 Medium)
- `DATABASE_URL`로 실제 연결이 열릴 때만 실행되고, 열리지 않으면 **건너뛴 사실을 남기며 통과**하는 테스트 파일.
- 재고 1인 상품에 대해 두 주문을 병렬로 실행 → 정확히 하나 성공, 재고 0, 주문 1건.
- 교착 시나리오: 두 주문이 상품 A·B를 반대 순서의 장바구니로 담고 병렬 실행 → 둘 다 500이 아닌 결과.
- 대응: REQ-ORDER-024, REQ-ORDER-032, REQ-ORDER-033.
- **선행 조건: 충족됨.** §0에서 CI DB 배선 소유권이 (B)로 확정되었으므로 M4는 그대로 진행한다 — 하네스는 이 SPEC이 만들고 `DATABASE_URL` 도달 가능 여부로 게이트한다. `.github/workflows/ci.yml`에 `services: postgres`를 추가하는 CI 필수 검사 승격은 M4의 범위가 아니며, 후속 CI SPEC(SPEC-CI-001 소유)이 담당한다.

### M5 — 보존 검증 (우선순위 Low)
- SPEC-ORDER-001 / SPEC-PAYMENT-001 / SPEC-STOREFRONT-001 기존 테스트 전량 회귀 확인.
- 대응: REQ-ORDER-031.

## §6. 위험

| 위험 | 성격 | 대응 |
|---|---|---|
| 실 DB 하네스가 CI에 배선되지 않아 검증 공백이 남는다 | 확정된 범위 밖 (§0 (B)) — 위험은 남아 있다 | 후속 CI SPEC(SPEC-CI-001 소유)이 배선하기 전까지 이 공백은 **열린 채로 유지**되며, `AC-013-EXCL-CONCURRENCY`는 개발자 기계에서만 닫힌다. M4는 하네스를 만들되 건너뛴 실행을 통과로 보고하지 않는다(REQ-ORDER-033) |

| 재고를 되돌릴 경로가 결제 취소뿐이라 재고가 영구히 잠긴다 | 범위 밖의 구조적 제약 (§0 확정) — 위험은 남아 있다 | 이 SPEC이 해결하지 않으며, 해결하는 척하지 않는다. 소유자 부재는 백로그 카드 `t21`이 이어받아 추적한다 |
