### §2.6 시로코 카테고리 재확인 — 차단 아님, 판단 재검토

`plan.md` §B.7이 시로코("스트레이트 팁 · 블랙 칼프")를 **더비로 잠정 배정**했으나, 원천은 이를 명시한 적이 없다. 실제 구두 용어에서 **블랙 칼프 스트레이트 팁은 옥스퍼드(클로즈드 레이싱)와 더 강하게 결부**되며, 더비(오픈 레이싱)는 두 번째 가설이다.

**요구 행위**: 라이브 원천(목업 Shop 화면의 필터 동작, 제품 카드의 분류 표시, 또는 UI Kit의 분류 어휘)에서 이 제품이 어느 카테고리에 속하도록 설계되었는지 확인한다.

| 확인 결과 | 조치 |
|---|---|
| 원천이 더비로 분류 | 현 배정 확정 |
| 원천이 옥스퍼드로 분류 | 5번째 카테고리 `옥스퍼드` 신설 또는 재배정 — 시드 스크립트 1개 값 |
| 원천이 분류하지 않음 | 몽크 건과 같은 기준으로 판단 — 거짓 분류를 피하는 쪽 |

**왜 이 항목이 있는가**: 이 SPEC은 몽크 스트랩을 더비로 부르는 것이 "공예 브랜드에 대한 사실상 거짓 진술"이라며 4번째 카테고리를 신설했다. 시로코에 같은 잣대를 적용하지 않으면 그 논리가 일관되지 않는다.

## §3. design phase가 결정해야 하는 시각 설계

### §3.1 품절 상품의 사이즈 그리드 표현

`plan.md` §B.1이 기록한 **의도적 이탈**을 시각적으로 어떻게 다룰지 결정한다.

- 원천(UI Kit): *일부* 사이즈만 `disabled`
- 이 SPEC: `stock === 0`이면 **전부** disabled, 아니면 **전부** 활성

전부-비활성 상태가 "품절 사이즈가 섞인 그리드"와 시각적으로 구분되어야 한다. 후보: 품절 상품은 사이즈 그리드 대신 UI Kit의 품절 태그 오버레이(불투명도 62% + 태그)를 사용.

**제약**: 어떤 결정이든 개별 사이즈에 서로 다른 상태를 부여해서는 안 된다(REQ-BRAND-023).

### §3.2 내비게이션 레이아웃

현재 `SiteHeader`는 `<header>` 안에 세션 분기 하나만 갖는다. 확장 후 담아야 할 것:

- 브랜드 로고 링크 (→ `/`)
- SHOP (→ `/shop`) · BESPOKE (→ `/bespoke`) · STORY (→ `/story`)
- CART (→ `/cart`)
- 기존 세션 분기 (로그인 링크 **또는** 내 정보 + 로그아웃)

UI Kit의 `.nav` 어휘를 참조하되, **컴포넌트 클래스 레이어를 새로 만들지 않는다** — 이 코드베이스는 Tailwind 유틸리티 + `@theme` 커스텀 프로퍼티로 스타일링한다(`research.md` §7 주의).

모바일 반응형 동작(6개 항목이 좁은 화면에 들어가는 방식)을 결정한다.

### §3.3 `/shop` 필터·정렬 컨트롤

- 카테고리 필터 버튼 **4개**(더비/로퍼/부츠/**몽크**) + 전체 — §3.5의 결정을 따른다. 목업은 3개만 보여주지만 `plan.md` §B.7이 몽크를 신설했다. 레이아웃은 4개(+전체=5)를 수용하도록 설계하되, §3.5가 3개로 되돌리면 버튼 하나가 사라지는 것 외에 레이아웃 변경이 없도록 **개수에 유연한 배치**를 택한다
- 버튼 목록은 `Category` 테이블에서 파생되므로(REQ-BRAND-014 / AC-BRAND-016) 개수를 하드코딩한 레이아웃은 금지한다
- 정렬 컨트롤: `newest` / `price_asc` / `price_desc` (기존 서비스가 지원하는 값 그대로)
- 선택 상태의 시각 표현
- URL 파라미터 기반이므로 각 컨트롤은 링크로 표현 가능(`plan.md` §B.5)

### §3.4 `/bespoke` · `/story` 페이지 레이아웃

정적 안내 페이지 2종. UI Kit의 **"주문 제작 안내" 콜아웃 블록**이 `/bespoke`의 자연스러운 골격이다.

**제약**: 폼·제출 버튼·장바구니 컨트롤을 두지 않는다(REQ-BRAND-019). 문의 폼이 UI Kit에 있으나 이 SPEC 범위 밖이다.

**사이즈 표기 확인**: `/bespoke` 카피는 브랜드 카피의 **"285mm부터 330mm까지"**를 따른다. 목업의 제품별 사이즈 범위 채움값(250mm/260mm 시작)과 어긋나지만, 후자는 인덱스 파생 합성값이므로 권위가 없다(`research.md` §3.3). 라이브 원천에서 브랜드의 실제 사이즈 범위를 재확인한다.

### §3.5 카테고리 개수 — 3개 vs 4개 (신규 결정 항목)

`plan.md` §B.7이 **4번째 카테고리 `몽크`를 신설**하기로 결정했다. 하야마("몽크 스트랩")를 더비로 분류하는 것이 제품에 대한 사실상 거짓 진술이기 때문이다.

**그러나 목업 필터 버튼은 3개다.** 4번째 추가는 디자인 원천으로부터의 **의도적 이탈**이며, design phase가 확인하거나 뒤집어야 한다.

| design phase 판단 | 결과 |
|---|---|
| 4개 승인 | 필터 버튼 4개. `/shop` 레이아웃이 4개(+전체=5)를 수용하도록 설계 |
| 3개 유지 | 하야마를 더비로 흡수. 변경 범위는 시드 스크립트 1개 값 — 필터 버튼이 `Category` 테이블 파생이므로 UI 코드 변경 없음 |

어느 쪽이든 **필터 버튼 목록을 하드코딩하지 않는다**(`plan.md` M5)는 제약이 이 결정을 값싸게 만든다.

## §7. D1 진입 시도 결과 (2026-09-07) — **DesignSync 도구 부재로 차단**

`manager-design`이 D1(연결 설정)을 시작하기 전에 DesignSync 도구의 운영 가용성을 확인했다.

**확인 방법**:
1. `.mcp.json` 전문 읽기 — 등록된 MCP 서버: `context7`, `moai`, `playwright` 3개뿐. `DesignSync`(또는 유사 명칭의 Claude Design 연동 서버) **미등록**.
2. 이 세션에 주입된 MCP 서버 사용 지침 블록 확인 — `claude.ai Lovable`, `claude.ai Supabase`, `context7` 3건만 존재. Claude Design/DesignSync 관련 지침 **없음**.
3. `.moai/config/sections/design.yaml` 확인 — `claude_design.enabled: true`로 설정은 되어 있으나, 이는 **정책 스위치**일 뿐 실제 도구 연결을 보장하지 않는다. `fallback_path: "code_based"`가 명시되어 있어, 설계상으로도 도구 부재 시 코드 기반 경로로 대체하도록 되어 있다.

**결론**: DesignSync 도구가 이 세션에 노출되어 있지 않다. 매니저 정의(`manager-design.md`) "Tool Availability (graceful degradation)" 절의 명시 규칙에 따라, D2-D5(디자인 시스템 생성/동기화, 화면 아티팩트 조회, 핸드오프 수신)는 **이 도구 없이는 실행 불가**하며, 대체 메커니즘(예: 일반 WebFetch로 claude.ai 접근)을 사용해서는 안 된다 — manager-design은 문서화된 DesignSync 도구 계약에만 결합한다.
