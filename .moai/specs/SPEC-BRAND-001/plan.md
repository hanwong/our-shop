# SPEC-BRAND-001 — 구현 계획

## §A. 배경

`our-shop`은 도메인 중립적 껍데기로 만들어져 왔고, SPEC-DESIGN-001이 그 위에 Classical 토큰 체계를 얹었다. 이 SPEC은 그 껍데기에 **"OUR"라는 구체적 브랜드**를 입힌다. 원천은 Claude Design 프로젝트 "OUR"이며, plan-phase에서 직접 읽어 `research.md`에 전문 고정했다.

`spec.md` §1.1이 못박은 구분이 이 계획 전체를 지배한다: **토큰 아키텍처는 SPEC-DESIGN-001 소유, 토큰 값만 이 SPEC 소유.**

## §B. 되돌리기 어려운 결정 (검토 우선)

아래 결정들은 **바뀔 가능성이 높은 순서**로 배치했다. 사람의 검토 주의력이 여기에 먼저 닿아야 한다. 실행 순서는 §F(의존성 순서)이며, 이 절과 다르다.

### §B.1 사이즈 비활성 상태를 무엇으로 결정하는가 — 가장 논쟁적

**결정**: 사이즈 옵션의 비활성 여부는 **`Product.stock === 0` 하나로만** 결정한다. 품절이면 5개 사이즈 **전부** 비활성, 재고가 있으면 **전부** 활성. 개별 사이즈가 서로 다른 상태를 갖는 일은 없다.

**대안과 기각 사유**:

| 대안 | 기각 사유 |
|---|---|
| 사이즈별 재고 컬럼 추가 | 스키마 마이그레이션 발생 → §2.2 무(無)마이그레이션 판정과 확정 결정 3에 정면 충돌 |
| 시드에 사이즈별 정적 플래그 심기 | 저장할 곳이 없다(스키마 변경 없이는). `description` 문자열에 인코딩하는 것은 데이터 모델 오용 |
| 제품 id 해시로 의사(pseudo) 품절 사이즈 생성 | **가짜 데이터를 진짜처럼 렌더링한다.** 사용자가 특정 사이즈를 못 산다고 믿게 만들며, 근거가 없다. 명백히 기각 |
| 어떤 사이즈도 비활성으로 렌더링하지 않음 | 목업의 품절 시각 언어를 전부 버린다. 재고 0 상품이 구매 가능해 보임 |

**감수하는 것(명시)**: 목업은 *일부* 사이즈만 품절로 보여준다. 이 결정은 그 시각을 그대로 재현하지 못한다 — 전부이거나 전무다. 이것은 **디자인 원천으로부터의 의도적 이탈**이며, design phase가 이 이탈을 어떻게 시각적으로 다룰지(예: 품절 상품은 사이즈 그리드 대신 "품절" 배지) 결정해야 한다.

**이 마일스톤이 위임 지시의 마일스톤 목록에 없었다는 사실**: 위임 지시의 마일스톤 열거에는 사이즈 UI가 없었으나, 확정 결정 3과 필수 AC 요구가 이를 전제한다. 따라서 M7로 **추론하여 추가**했다. 이 추론이 틀렸다면(사이즈 UI가 이번 범위 밖이라면) M7·REQ-BRAND-022/023·대응 AC를 통째로 삭제하면 되며, 다른 마일스톤에 영향이 없도록 격리해 두었다.

### §B.2 로고 파일 선택 — design phase 미결 항목

두 에셋 `logo_mono_black.png`와 `logo_gold_only.png`가 있으나, **이 프로젝트의 팔레트에는 골드가 더 이상 존재하지 않는다**(`--color-accent`가 `#b68235` 골드에서 `#2b2b2b` 다크 그레이로 바뀜). 즉 `logo_gold_only.png`라는 **파일명이 현재 팔레트와 모순**된다.

두 해석이 모두 가능하다:
- 파일명이 낡았고 실제 픽셀은 이미 그레이스케일이다.
- 에셋이 낡았고 실제 픽셀이 골드다(그렇다면 팔레트와 충돌하므로 사용 불가).

**픽셀을 보지 않고는 판별할 수 없다.** 따라서 이것을 design phase 질문으로 남긴다.

**근거 있는 잠정 기본값**: `logo_mono_black.png`. 이름과 팔레트가 모순되지 않는 유일한 후보이며, 그레이스케일 전용 팔레트에서 모노 블랙은 정의상 안전하다. **단서**: design phase(manager-design)가 라이브 원천을 재조회하여 두 파일의 실제 픽셀을 확인하고 이 기본값을 확정하거나 뒤집어야 한다.

### §B.3 제작 기간 "4주" vs "4개월" — 판단 근거 명시

원천 안에서 값이 충돌한다.

| 값 | 출처 | 출현 횟수 |
|---|---|---|
| **4주 / 약 4주** | `OUR Store.dc.html` 목업 본문 카피 | **3회, 일관됨** |
| 4개월 | 프로젝트 카드의 원천 노트 | 1회 |

**결정**: **"약 4주"를 채택**한다. 근거는 다수 일관성 — 실제 디자인 산출물(사용자에게 보일 카피가 실제로 들어 있는 파일) 안에서 3회 일관되게 나타나는 값이, 부수적 노트에 1회 나타나는 값보다 강한 증거다. 수제화 업계 통례로도 4주가 4개월보다 개연적이다.

**이것은 판단이지 사실이 아니다**: "4개월"은 전사 과정의 오기(誤記)로 보이나, 확인되지 않았다. design phase가 라이브 Claude Design 원천에 대해 이 값을 **재확인**해야 하며, 만약 4개월이 옳다면 REQ-BRAND-017과 `/bespoke` 카피가 함께 수정된다.

### §B.4 `public/` 컨벤션 — 저장소 최초 결정

`public/` 디렉터리가 저장소에 **아예 없다**(확인 완료). 이 SPEC이 컨벤션을 0에서 만든다.

**결정**:
- 경로: `public/brand/` — 브랜드 에셋 전용 하위 디렉터리. 루트에 직접 두면 향후 파비콘·OG 이미지·제품 사진이 섞여 구분이 사라진다.
- 렌더링: `next/image`의 `Image` 컴포넌트.

**정정 사항 (위임 지시의 전제와 다름)**: 위임 지시는 `next/image` 사용 여부가 그린필드일 가능성을 열어두었으나, **이미 선례가 있다** — `src/components/product/ProductCard.tsx:1`과 `ProductGallery.tsx:3`이 `next/image`를 임포트한다. 따라서 이것은 새 결정이 아니라 **기존 선례를 따르는 것**이며, 그만큼 논쟁 여지가 적다.

### §B.5 `/shop`의 필터 상호작용 방식

**결정**: URL 검색 파라미터(`?category=<slug>&sort=<sort>`) 기반. 서버 컴포넌트가 `searchParams`를 읽어 `listProducts`에 그대로 전달한다.

**근거**: `listProducts`가 이미 `URLSearchParams`를 받는다(`(shop)/page.tsx:19`가 `listProducts(new URLSearchParams())`로 호출). 클라이언트 상태를 도입하면 이 계약을 우회하게 되고, 서버 컴포넌트인 홈과 구현 방식이 갈라진다. URL 기반은 공유·뒤로가기·북마크가 공짜로 따라온다.

**감수하는 것**: 필터 클릭마다 서버 왕복이 발생한다. 카탈로그 규모(시드 6개)에서 문제되지 않으며, 성능이 문제가 되면 그때 클라이언트 캐싱을 얹는 것이 역순보다 싸다.

### §B.6 헤더 확장의 범위 — 구조는 건드리지 않는다

`SiteHeader.tsx`는 현재 `<header>` 안에 **로그인 상태 분기 하나만** 렌더링한다(확인 완료). 이 SPEC은 그 안에 로고 + 4개 내비 링크를 추가한다 — 내용상 실질적 확장이다.

**결정**: 컴포넌트의 **구조적 배치는 절대 건드리지 않는다.** 파일은 계속 `src/app/(shop)/layout.tsx`에서만 렌더링되며, 루트 레이아웃으로 올리지 않는다. SPEC-AUTH-004가 고친 결함(고객용 로그아웃 버튼이 관리자 세션을 끊는 문제)이 정확히 그 이동으로 되살아나기 때문이다. `layout.tsx`의 `@MX:NOTE`가 이 위험을 이미 경고하고 있다.

### §B.7 모호한 제품 2건의 카테고리 배정 — 비대칭 판단

목업 필터 버튼은 3개(더비·로퍼·부츠)다. 6개 제품 중 **4개는 부제가 카테고리를 명시**하지만, 2개는 그렇지 않다.

| 제품 | 부제 | 문제 |
|---|---|---|
| 시로코 | "스트레이트 팁" | *토 스타일*을 말한다 — 3개 필터 어디에도 해당 없음 |
| 하야마 | "몽크 스트랩" | *잠금 방식*을 말한다 — 관례상 독립 카테고리 |

**결정 (두 건을 서로 다르게 처리한다)**:

- **시로코 → 더비 (잠정, design phase 재확인 대상).** 스트레이트 팁은 **토 스타일**이며 끈 방식과 **직교**한다 — 모든 끈 구두는 어떤 토 스타일이든 갖는다. 따라서 "더비"로 부르는 것이 부제와 **모순되지는 않는다**.

  **다만 이것은 추론이지 원천의 진술이 아니다.** 원천은 시로코를 더비라고 **말한 적이 없다** — 부제는 "스트레이트 팁 · 블랙 칼프"뿐이다. 그리고 대립 가설이 있다: **블랙 칼프 스트레이트 팁은 실제 구두 용어에서 더비(오픈 레이싱)보다 옥스퍼드(클로즈드 레이싱)와 더 강하게 결부된다.** 정장용 블랙 칼프 스트레이트 팁 = 옥스퍼드가 업계 관행에 가깝다.

  **자기 적용 (plan-audit iter1 D10)**: 이 SPEC은 바로 아래에서 "몽크를 더비라 부르는 것은 공예 브랜드에 거짓 분류를 씌우는 것"이라는 논리로 4번째 카테고리를 신설했다. 같은 잣대를 시로코에도 적용해야 한다 — 옥스퍼드일 가능성이 실재하는데 "모순되지 않는다"는 약한 근거만으로 더비로 확정하는 것은 몽크 건에서 거부한 바로 그 추론이다.

  **따라서 이 배정은 "확정"이 아니라 "잠정"이다.** `design.md` §5 체크리스트에 로고 파일·제작 기간과 나란히 **시로코 카테고리 재확인** 항목을 올렸다. design phase가 라이브 원천에서 이 제품의 의도된 분류를 확인하며, 옥스퍼드로 판명되면 5번째 카테고리 신설 또는 재배정이 필요하다(변경 범위는 시드 스크립트 1개 값).
- **하야마 → `몽크` 카테고리 신설 (4번째).** 몽크 스트랩은 **잠금 방식**(버클)이며 더비(끈)와 **상호 배타적**이다. 몽크를 더비라 부르는 것은 제품에 대한 **사실상 거짓 진술**이다.

**비대칭의 근거**: 두 부제가 말하는 것의 *종류*가 다르다. 하나는 카테고리와 독립인 축(토 스타일), 다른 하나는 카테고리와 경쟁하는 축(잠금 방식). 전자는 흡수 가능하고 후자는 아니다.

**왜 이 구분이 중요한가**: 이 사이트는 "한 켤레씩 손으로 꿰맨다"는 공예 전문성으로 포지셔닝한 수제화 브랜드다. 구두를 아는 방문자에게 몽크 스트랩이 "더비"로 분류된 것은 눈에 띄는 오류이며, 데이터 흠결이 아니라 **신뢰도 비용**이다.

**4번째 카테고리의 비용**: `Category` 행 1개 + 필터 버튼 1개. 필터 버튼은 하드코딩이 아니라 `Category` 테이블에서 파생시키므로(M5 구현 지침) 추가 비용이 사실상 없다.

**부수 효과 — 분포가 개선된다**:

| 배정 | 3개 카테고리로 강제 | 4개 카테고리 (채택) |
|---|---|---|
| 더비 | **4** (에지마·아키타·시로코·하야마) | 3 (에지마·아키타·시로코) |
| 로퍼 | 1 | 1 |
| 부츠 | 1 | 1 |
| 몽크 | — | 1 |

강제안은 6개 중 4개가 한 카테고리에 몰려 필터가 사실상 무의미해진다. AC-BRAND-015(필터가 **진부분집합**을 만들 것)는 양쪽 다 통과하지만, 채택안이 필터를 실제로 유용하게 만든다.

**감수하는 것 (명시)**: 목업은 필터 버튼을 **3개**만 보여준다. 4번째를 추가하면 `/shop`이 디자인 원천과 시각적으로 어긋난다. 이는 **의도적 이탈**이며 design phase 확인 대상이다(`design.md` §3.5). design phase가 3개 유지를 택하면 하야마를 더비로 흡수하고 이 결정을 뒤집으면 되며, 변경 범위는 시드 스크립트 1개 값이다.

**2026-09-07 갱신 — design.md §3.5로 뒤집힘.** design phase가 라이브 Claude Design 재조회로 실제 Shop 화면 필터 버튼을 확인한 결과 정확히 3개(더비/로퍼/부츠)였고, "몽크" 카테고리는 원천에 존재하지 않았다. 위 §B.7의 판단(하야마 → 몽크 카테고리 신설, 4개 채택)과 위 비교 표의 "4개 카테고리 (채택)" 열은 plan-phase 판단의 기록으로 그대로 보존하되, **최종 채택 상태는 3개 카테고리**다 — 하야마는 시로코와 같은 근거(원천에 전용 카테고리 없음)로 더비에 재배정되었다(`design.md` §2.6/§3.5, `research.md` §3.2 갱신 참조).

## §G. 안티패턴 (범하지 말 것)

- `@theme` 프로퍼티 **이름**을 손대는 것 — SPEC-DESIGN-001 재개봉으로 읽힌다
- `SiteHeader`를 루트 레이아웃으로 이동 — SPEC-AUTH-004가 고친 결함 재발
- `/shop`용 새 리포지토리·서비스 함수 작성 — `listProducts` 재사용이 요구사항
- 사이즈별 비활성 상태를 데이터 없이 지어내는 것(§B.1)
- `product.md`를 손으로 고치는 것(spec.md §3)
- 시드 스크립트를 npm 스크립트로 배선하는 것 — 기존 두 시드 스크립트 모두 배선되어 있지 않다
- **원천 `styles.css`를 통째로 복사하는 것** — `--color-accent-2-*` 램프 추가(REQ-BRAND-007 위반)와 폰트 리터럴 되돌리기(t51 승인 수정 무효화)를 동시에 일으킨다(`research.md` §4.2)
- **`i % 3` 파생 사이즈 범위 문자열을 시드하는 것** — 합성 채움값을 제품 데이터로 굳힌다(`research.md` §3.3)
- **`/shop` 필터 버튼 목록을 하드코딩하는 것** — 카테고리 개수가 design phase에서 뒤집힐 수 있다(§B.7)
