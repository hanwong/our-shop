### Task-requested item 2 — Root-cause finding: the recurring M6 scope-undercounting pattern

**Root cause (independently confirmed, not merely re-stated from progress.md)**: M6's scope is defined *functionally* — "every test assertion that a signature change made elsewhere in this SPEC mechanically breaks" — rather than *enumeratively*. That functional definition is not fully computable from static reading of the call graph at plan-phase or even at early run-phase, because:

1. The affected-file set is the **transitive closure of every caller of every signature that changes** (`createOrder`, `CreateOrderRow`, `findCartByUserId`, the schema itself), and Milestones M1→M5 change those signatures **incrementally** across five separate commits. A test file that calls `order-service.ts` indirectly through a fixture or a helper (e.g., `cart-repository-tx.test.ts`'s assertion about `findCartByUserId`'s arity) is invisible to a static grep for the SPEC's own listed target files — it only becomes visible once the actual type-check or test run is executed against the tree *after* the relevant milestone has landed.
2. Each of the three (now four, counting F3) undercounts happened at a point where only a **subset** of the milestones had landed: the plan-phase estimate (M0, before any code existed) could only reason from file *names* it expected to be affected; the M1-only re-scan (`grep -rln "schema.prisma" tests/`) could only see schema-literal assertions, not TypeScript compile-time fallout from `CreateOrderRow`/`createOrder`'s signature, which does not exist until M3/M4 land; and the M3/M4-landed re-scan still could not see M5's screen-level fixture requirement (`checkout-complete-page-payment.test.tsx`) until M5's screens actually existed. Each earlier count was a *correct* snapshot of what was mechanically knowable at that point in the sequence — it was never a research error in the sense of a missed grep, it was a structural impossibility of knowing the full set before its producing milestone landed.
3. This is confirmed by the SPEC's own accounting: every one of the four undercounts was found by **running the actual tool** (`tsc`, `vitest`) against the tree *after* landing a milestone, never by a sharper static read of an *earlier* tree state.

**Recommendation**: `research.md`'s M6 section should be reworded from "the scope is N files / M items" (a number that has now been wrong four times, always upward) to describing the **counting method**: *"After each milestone that changes a shared signature (M1 schema, M3 repository, M4 service) lands, run `npx tsc --noEmit` and `npx vitest run --reporter=dot` against the full corpus and enumerate every newly-failing file as an M6 rewrite target. Do not assert a fixed file/item count before every signature-changing milestone (M1, M3, M4, M5) has landed — the true M6 footprint is only fully knowable after M5, not at plan-phase."* This is a **mechanical, no-design-judgment doc edit** `manager-spec` can make directly (the actual final list of 14 files is already fully known and enumerable from this SPEC's own commits) — it does not require a new Socratic round or a scope decision.

**Process note for future Tier L SPECs** (broader than this SPEC, for the harness/process layer, not just this correction): whenever a milestone's Definition-of-Done is phrased as "whatever mechanically breaks due to a signature change landing elsewhere in this SPEC," the research/plan artifacts should from the outset state the counting METHOD (re-run full suite after each dependency milestone; treat the enumerated set as provisional until the last dependency lands) rather than a specific number. A number invites being treated as ground truth and re-cited without re-verification (exactly what happened here four times); a method survives being re-applied at each milestone boundary without becoming stale. This is a process/documentation-authoring recommendation, not a code or runtime change — no Go/hook work is implied.
