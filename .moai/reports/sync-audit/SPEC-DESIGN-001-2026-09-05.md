## FormField Fix — Re-verified (this pass)

**CodeRabbit finding**: `src/components/ui/FormField.tsx` spread `sharedProps` (FormField's own computed `id`/`className`/`aria-invalid`/`aria-describedby`) BEFORE `rest` (caller-passed props) — `{...sharedProps} {...rest}` — so any overlapping key the caller passed always won, silently overriding FormField's own computed error-linking attributes even when `error` was genuinely set.

**Fix applied** (verified by direct read of the current `FormField.tsx`):

```tsx
const sharedProps = {
  id,
  className: fieldInputClassName({ className }),
  ...(error ? { "aria-invalid": true as const, "aria-describedby": errorId } : {}),
};
...
<textarea {...(rest as ...)} {...sharedProps} />   // rest FIRST, sharedProps LAST
<input {...(rest as ...)} {...sharedProps} />
```

### 1. Mechanical correctness — walked through both cases directly

- **Error set + caller overlap** (e.g. `<FormField error="bad" aria-describedby="caller-hint" aria-invalid={false} />`): `sharedProps` contributes real `aria-invalid: true` / `aria-describedby: "<id>-error"` because `error` is truthy. Spread order puts `sharedProps` LAST, so these win over whatever `rest` (caller) supplied. Confirmed by direct reasoning through JSX spread semantics (later spread overrides earlier for the same key) — the fix's intended direction.
- **No error + caller-supplied hint** (e.g. `<FormField aria-describedby="stock-hint" />`, no `error` prop): `sharedProps`'s conditional spread `...(error ? {...} : {})` contributes **zero** aria-* keys at all — not even `undefined` placeholders. So `sharedProps` spread last has nothing to override, and the caller's `aria-describedby`/`aria-invalid` from `rest` survive untouched. This conditional-emptiness (as opposed to a naive unconditional `"aria-describedby": errorId` where `errorId` is `undefined`) is what makes the order flip safe — an unconditional version would have overridden the caller's real value with an explicit `undefined`, wiping the attribute. Confirmed this is exactly what the fix does (not merely order flip alone).

Both cases produce the intended attribute values. The fix is mechanically correct.

### 3. `ProductForm.tsx`'s actual call sites — re-checked directly

`grep -n "<FormField" src/app/staff/products/ProductForm.tsx` → **4** call sites (`name` line 199, `price` line 232, `stock` line 245, `description` line 270) — see § Accuracy Note below regarding the "5" figure used in both the dispatch and `progress.md`.

For each of the 4: read the JSX directly — none of them passes an `error=` prop to `FormField` (ProductForm renders its own error text via a separate `fieldError()` helper, not FormField's built-in `error` mechanism). Each does pass its own `aria-describedby={describedBy(...)}`. Confirmed via `grep -n 'error=\|errors\[' ProductForm.tsx` that `error=` is never passed to any FormField instance in this file — only `errors[field]` lookups feeding the separate `fieldError()`/`describedBy()` helpers.

Consequence, walked through directly:
- **When a field has a validation error** (`errors[field]` truthy): `describedBy()` returns e.g. `"name-error"`. `FormField`'s own `error` prop is still never set → `sharedProps` conditionally contributes **no** aria-* keys → `rest`'s `"name-error"` passes through untouched in the current (fixed) code. Correct — the error-referencing id ProductForm computed itself is preserved.
- **When a field has no error**: `describedBy()` returns `undefined` or (for `stock`) the static hint id `"stock-hint"` — again preserved untouched by the same conditional-emptiness mechanism.

Both states behave correctly in the current code. Confirmed no regression for any of ProductForm's 4 real call sites.

### Accuracy Note (non-blocking — does not change the verdict)

Two related overstatements in the motivating narrative, checked independently against the actual code rather than accepted on assertion (per this audit's skeptical-evaluation stance):

1. **Call-site count**: both this task's dispatch and `progress.md`'s own new subsection say ProductForm.tsx has "5" `<FormField>` call sites. `grep -n "<FormField" src/app/staff/products/ProductForm.tsx` shows **4** (`name`, `price`, `stock`, `description`); the `categoryId` field at line ~216 uses a raw `<select>`, not `<FormField>` (a code comment at line 209 explicitly says so — likely the miscount's source, since the comment itself contains the substring `<FormField>`).
2. **"Active" vs. "latent" defect**: the dispatch framed this as an "ACTIVE bug... not just theoretical" specifically because of ProductForm's call sites. Read against the actual old spread order (`{...sharedProps} {...rest}`, rest wins unconditionally), ProductForm was **never actually broken by the original bug** in any released state — since ProductForm never sets FormField's own `error` prop, `rest` (its own `aria-describedby`) always won in the old code too, which is the behavior ProductForm actually wants. The scenario CodeRabbit's finding describes (a caller's manual `aria-*` clobbering FormField's *real, error-linked* computed value) requires a consumer that sets BOTH `error=` AND a manual `aria-describedby`/`aria-invalid` — verified via `grep` across all 9 files that import `FormField` that **no current consumer does both**: `ProductForm.tsx` passes manual `aria-describedby` but never `error=`; `CheckoutForm.tsx`/`OrderLookupForm.tsx` pass `error=` but never manual `aria-*`. This matches `progress.md`'s own, more careful wording ("Verified as a genuine LATENT defect... no current consumer simultaneously passes `error=` AND a manual `aria-describedby`") — the progress.md author's own analysis is accurate; the "5"/"ACTIVE" framing in the dispatch (and the progress.md subsection's own header sentence, which uses "5" in the same breath as its own correct latent-defect conclusion) is the part that overstates it.

**Why this doesn't move the verdict**: the fix is correct and beneficial regardless of whether the defect was live or latent — it closes a real hole in the component's contract before any future consumer trips it, and the regression tests are genuine either way. This is a precision note on how the defect should be described (latent hardening, not an active production bug being fixed under fire), not a defect in the fix itself.

**Conclusion**: the FormField finding is genuinely resolved. Mechanically correct in both branches, covered by tests that would actually catch a regression to either the original bug or the naive alternative fix, scoped to exactly the claimed 3 files, and verified not to change ProductForm.tsx's real-world behavior.
