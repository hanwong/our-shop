## Findings

### F1 [CRITICAL] [blocking] `src/app/globals.css` + `src/app/layout.tsx` — Classical typography (Cormorant Garamond / Lora) is not visually applied anywhere on the site except `SiteHeader.tsx`

**This is the single most important finding of this audit — a token-value/visual mismatch between the SSOT and the shipped code, per the audit brief.**

Verified independently via static analysis (not inference from a text pattern alone — this was cross-checked against the actual CSS cascade mechanics and confirmed by exhaustive grep):

1. `grep -rln "font-heading\b" src/` → **only `src/app/globals.css` itself** (the token declaration). The `font-heading` Tailwind v4 auto-generated utility class is used **zero times** on any actual heading element anywhere in `src/`.
2. `grep -rn "font-body" src/` → used exactly **once**, in `src/components/layout/SiteHeader.tsx`. Every other page/component that renders text (all 15 pages' `<h1>`/`<h2>` headings, every paragraph, every form field, every button) uses no `font-heading`/`font-body` utility at all.
3. `layout.tsx` applies `next/font/google`'s two className tokens to `<html>`: `className={`${cormorantGaramond.className} ${lora.className}`}`. Neither font call sets the `variable:` option, so no `--font-cormorant-garamond`/`--font-lora` CSS custom property is generated — only two scoped `.className { font-family: ... }` rules with equal (single-class) specificity, applied to the same element. Which one visually wins for `<html>` itself is a source-order tie that this code does not control.
4. Independently and more decisively: `src/app/globals.css` carries a pre-existing (SPEC-STOREFRONT-001-era) rule — **untouched in substance by this SPEC, only its comment was edited**:
   ```css
   body {
     font-family: ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto,
       "Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR", sans-serif;
     ...
   }
   ```
   This is a **direct declaration on `<body>`**. Per CSS cascade/inheritance mechanics, an element's own explicit declaration for a property always governs that element (and is what its descendants inherit from) — it is not in a specificity contest with a rule that targets a *different* element (`<html>`). Every visible page element lives inside `<body>`, so every page element inherits font-family from `<body>`'s own rule, **not** from `<html>`'s `next/font` classes. The `next/font` classes on `<html>` have no visible effect on anything, because nothing renders text directly at the `<html>` level.
5. The new SPEC-DESIGN-001 comment on that same `body` rule states it is meant to be "the Korean-copy fallback stack **for text outside the two Classical font roles**" — this describes the *intended* behavior, but is not how CSS actually resolves here; the implementer's mental model of the cascade does not match the mechanics in (4).
6. No test in the repository (including the 6 new/modified SPEC-DESIGN-001 test files, all independently re-run and green) asserts anything about rendered `font-family` — `grep -rn "font-family\|getComputedStyle" tests/` → 0 hits. The vitest `next/font/google` mock (`tests/mocks/next-font-google.ts`) returns a synthetic `{ className, style: { fontFamily } }` object but is never asserted against, so this gap is invisible to the entire test suite by construction.

**Net effect**: `next/font/google` fetches and self-hosts Cormorant Garamond + Lora at build time (so plan.md §B.5's stated network-request tradeoff is real), but the fonts are not rendered on any page's headings or body copy anywhere in the shipped product except the one component that explicitly opts in with its own `font-body` utility class.

**Secondary, compounding observation (not itself blocking, but relevant to whether "fixing the cascade" alone suffices)**: Cormorant Garamond and Lora are Latin-only serif faces with no Hangul glyph coverage. The overwhelming majority of this site's copy is Korean (headings like "장바구니", "주문 조회", "상품 수정", etc.). Even if the cascade conflict in (4) were fixed and `font-heading`/`font-body` were applied via Tailwind utilities on every heading/body element, Korean glyphs would still fall through each token's own fallback (`system-ui, sans-serif`) rather than the curated Korean stack (`Apple SD Gothic Neo` → `Malgun Gothic` → `Noto Sans KR`) that the pre-existing `body` rule provides — so a naive fix (just applying `font-heading`/`font-body` everywhere) would trade one problem (no Classical font applied) for another (worse Korean font fallback than what currently ships). This needs a considered fix, not a one-line patch.

**This directly falsifies**:
- **AC-DESIGN-010**: "15개 페이지 전부가 Classical 타이포그래피(`--font-heading`/`--font-body`)와 배경(`--color-bg`)을 상속한다" — the background half holds (`bg-bg text-text` on `<body>` in `layout.tsx` is a direct Tailwind utility on `<body>` itself, so it is not shadowed the way `font-family` is); the **typography half does not hold**, verified false by the analysis above, not merely unconfirmed. The AC's own verification instruction ("타이포·배경 상속은 layout.tsx 단일 지점에서 오므로 페이지별 개별 확인 불필요") assumed the single point actually delivers both — it delivers only one of the two.
- **AC-DESIGN-003(b)** in spirit: the fonts are "loaded" in the narrow sense of being fetched/self-hosted, but the AC's parenthetical framing ("Cormorant Garamond(제목)·Lora(본문)") — headings in one, body in the other — describes a differentiated per-role application that does not exist anywhere in the shipped code.

**Required fix**: Resolve the cascade conflict deliberately (e.g., apply `font-heading` to a heading-level selector or shared heading component, apply `font-body` to `<body>` itself instead of relying on `<html>`-level next/font classes, and preserve the Korean-script fallback chain for Hangul content — e.g. declare `--font-heading`/`--font-body` with the Korean fallback stack appended, or scope the Latin serif application to a wrapper class that only affects non-Korean content per plan.md's own "Latin stack ahead of platform Korean faces" precedent). Add at least one test that would fail if this regresses again (a static scan asserting `font-heading`/`font-body` utility usage count across headings, since jsdom cannot verify actual computed font-family from CSS files).
