### Findings (structured defect-list)

- **F1** [Low] [optional] `src/features/admin/repositories/admin-order-repository.ts:170-215` — `cancelOrderAsAdmin()`'s stock-restore/coupon-release loop duplicates `payment-repository.ts`'s `markOrderCancelledAndRestoreStock()` shell rather than sharing it (design.md §4's explicit WET tradeoff — `payment-repository.ts` is SPEC-PAYMENT-001-owned and not modified by this SPEC). Independently re-read both implementations line-by-line: they are behaviorally identical (same `updateMany` shape, same stock-increment loop, same coupon-release call sequence via the shared `findCouponByCode`/`decrementRedeemedCountIfPositive` functions, same `coupon === null` silent-skip handling). Not a defect today, and already flagged in-source via `@MX:NOTE` naming a future cross-SPEC refactor target. Required fix (if pursued later, out of this SPEC's scope): extract the shared shell into a `stock-restore.ts` utility once a third caller justifies the abstraction.

- **F2** [Info] [optional] Two-admin concurrent-cancel race (`AC-ADMIN-EXCL-CONCURRENCY`) is verified only by static form inspection (`cancelOrderAsAdmin`'s `updateMany` WHERE clause includes source status, matching the same conditional-atomic-update pattern SPEC-ORDER-002 established), not by a live-PostgreSQL concurrency test. This exclusion is explicitly declared in `acceptance.md` itself (`## 잠재적 §0 제외 후보`) and CHANGELOG.md's "알려진 한계" section, mirroring `SPEC-ORDER-002`'s identical, already-accepted exclusion shape. Not a gap this SPEC introduced — a pre-existing, disclosed project-level testing-environment constraint (no live PostgreSQL in this dev environment, confirmed by other integration tests in the suite hitting the same constraint).

- **F3** [Info] [optional] `src/app/staff/login/page.tsx` always redirects to `/staff/orders` on any successful login response, regardless of the authenticated user's role (per CHANGELOG: "성공 시 응답 본문 내용과 무관하게 항상 `/staff/orders`로만 이동한다 — 역할 분기 없음"). The actual admin-vs-customer rejection is deferred to `/staff/orders`'s server-side gate (`resolveAdminSession()` before any data fetch — test-verified, §Evidence E4). This is spec-correct (AC-ADMIN-006 requires no data exposure, not client-side role branching) and avoids a second place to get the reason-blind rejection logic wrong, but produces one extra client-side redirect hop for a rejected non-admin login. No security or functional impact — noted for completeness only.

No blocking findings.
