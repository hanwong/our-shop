### 5. Source review — `SiteHeader.tsx` and `LogoutButton.tsx` (Read, not summarized)

- **CSRF wiring correctness**: `LogoutButton.tsx` reads `csrf_token` via inline `document.cookie` regex parse (same pattern as `CancelOrderButton.tsx`/`ProductForm.tsx`), sends it as `X-CSRF-Token` request header via `fetch(..., { headers: { "X-CSRF-Token": readCsrfToken() } })`. `csrf.ts`'s `verifyCsrfRequest()` reads `request.headers.get("x-csrf-token")` (HTTP header names are case-insensitive per the Headers/Request spec, and `csrf.ts`'s own doc comment expects exactly this double-submit shape) and compares it against the `csrf_token` cookie value read server-side. The client and server sides correctly implement the same double-submit contract — verified by reading both files side by side, not merely by pattern name.
- **No XSS/injection surface**: `grep -n "dangerouslySetInnerHTML\|eval(\|new Function(" ...` → 0 matches. No dynamic HTML injection, no string-to-code evaluation. All rendered content is static Korean text or `next/link` hrefs with literal string values.
- **No client-side auth-state storage (REQ-AUTH-048)**: `grep -niE "Authorization|Bearer|localStorage|sessionStorage|createContext|useContext|useAuth" SiteHeader.tsx LogoutButton.tsx` → 0 matches (exit 1). `LogoutButton` takes no props and holds no session-derived state; `SiteHeader` computes `session` locally on the server and does not pass it through any client-observable channel other than conditionally rendering `<LogoutButton />`.
- **Session-null-reason collapse (REQ-AUTH-040)**: structurally guaranteed, not just tested — `resolveSession()`'s return type is `Promise<Session | null>` (`Session = { userId: string; role: "customer" | "admin" }`), with no reason field anywhere in the type. `SiteHeader` branches only on `session === null`. There is no channel through which a reason could leak even if the component tried.
