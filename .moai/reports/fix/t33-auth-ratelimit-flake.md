# Card t33 — AC-AUTH-021 로그인 rate-limit 테스트가 전체 스위트 실행 시 간헐 실패

Class B (원인 미확정 결함) — `plan` 생략, `run`이 원인 규명 + 수정 둘 다 담당.
대상 파일: `tests/unit/api/auth/login.test.ts` (테스트 파일만 수정, 프로덕션 코드·보안 로직 무변경).

t20(AC-AUTH-005)과는 별개의 두 번째 플레이크이며, 원인을 별도로 규명했다 — t20의 원인(두 통계 그룹 간 시간축 교란)과 이 카드의 원인(단일 절대 시간창 초과)은 서로 다른 메커니즘이다. 실제로 t20의 자체 보고서(`t20-auth-timing-flake.md` §5 잔여 위험)가 "이 세션의 두 전체 스위트 실행 모두에서 AC-AUTH-021의 간헐 타임아웃이 재현됐다"고 이미 기록해 두었다 — 같은 고부하 조건에서 독립적으로 관측된 사실이다.

## 1. Claim (주장)

`AC-AUTH-021` 테스트("returns 429 after more than 5 requests/60s ...")가 전체 스위트 실행 시 간헐 실패하는 근본 원인은 **절대 시간창(60초) 소진**이다: 이 테스트는 실제 bcrypt(cost 12) 기반 로그인 요청 6회를 순차 실행하며, `checkRateLimit()`이 카운트하기 *전에* 60초보다 오래된 타임스탬프를 먼저 걸러내므로(`rate-limit.ts`의 `timestamps.filter((t) => now - t < WINDOW_MS)`), 6회 요청의 실제 경과 시간이 60초에 근접·초과하면 가장 오래된(1번째) 타임스탬프가 6번째 요청 판정 시점에 이미 창 밖으로 밀려나 카운트가 6에서 5로 줄어들고, 6번째 요청이 429가 아닌 200으로 통과해 버린다. 이 메커니즘을 페이크 타이머로 결정론적으로 재현했고(§2), REQ-AUTH-021의 실제 프로덕션 60초 임계값·잠금 로직은 한 글자도 건드리지 않은 채 테스트의 시계만 고정(freeze)하는 방식으로 수정했다.

## 2. Evidence (증거)

### 원인 규명 — 메커니즘 직접 재현 (수정 전, 결정론적 RED)

`vi.useFakeTimers()`로 시계를 제어해, 실제 시스템 부하 없이도 "6회 요청 사이 경과 시간이 60초를 넘으면 어떻게 되는가"를 결정론적으로 관측했다. 5회 요청 각각의 뒤에 13초씩 시계를 전진시켜(총 경과 65초), 실제 `POST` 라우트 핸들러를 그대로 호출했다:

```
$ npx vitest run tests/unit/api/auth/login.test.ts -t "AC-AUTH-021"
 × [SPEC-AUTH-001 M6 / AC-AUTH-021] ...
   AssertionError: expected 200 to be 429
```

6번째 요청이 429가 아니라 200을 반환함을 확인 — 가설이 정확함을 실제 라우트 코드로 직접 증명했다(재현 스크립트는 수정 커밋에 포함되지 않음, 아래 수정된 최종 테스트 자체가 이 메커니즘을 프로덕션 코드 변경 없이 회피하도록 재작성됨).

### 원인 규명 — 격리 실행 기준선 (수정 전)

```
$ npx vitest run tests/unit/api/auth/login.test.ts -t "AC-AUTH-021"   (3회 반복)
 ✓ (1 test) 1399ms / 1339ms / 1354ms
```

격리 실행에서는 6회 요청이 ~1.3-1.4초에 끝나 60초 창에 여유가 크다 — 그래서 격리 실행에서는 재현되지 않고, 전체 스위트의 CPU 경합(다른 파일들의 동시 real-bcrypt 호출) 하에서만 간헐적으로 경과 시간이 창을 위협할 만큼 늘어난다.

### 수정 (테스트 파일만)

- `tests/unit/api/auth/login.test.ts`: AC-AUTH-021 테스트에 `vi.useFakeTimers({ now: <고정 시각> })`를 추가해 `Date.now()`를 6회 요청 내내 고정시켰다. `shouldAdvanceTime`는 지정하지 않음(기본값 false) — 실제 bcrypt Promise는 마이크로태스크 큐를 통해 정상적으로 real-time에 resolve되지만(네이티브 비동기 I/O는 페이크 타이머의 영향을 받지 않는다), rate limiter가 관측하는 `Date.now()`만 고정되어 6회 요청이 실제로 얼마나 걸리든 항상 "동시"로 취급된다. `try/finally`로 `vi.useRealTimers()`를 보장.
- REQ-AUTH-021의 60,000ms 윈도우·15분 잠금·`MAX_REQUESTS_PER_WINDOW=5` 등 `src/lib/auth/rate-limit.ts`의 프로덕션 로직은 전혀 수정하지 않았다 — t20이 확립한 원칙(테스트 방법론을 고치되 실제 허용오차·임계값은 건드리지 않는다)을 그대로 따랐다.

### 수정 후 검증 — 같은 결정론적 재현으로 견고성 확인 (GREEN)

수정 전 RED를 만들었던 것과 동일한 "5회 요청 뒤 13초씩 전진, 총 65초 경과" 시나리오를 수정된 테스트에 임시로 적용해 재확인 — 시계가 고정된 상태에서는 그 전진 로직 자체가 무의미해짐을 실제로 확인한 뒤(고정 시계는 수동 전진이 없는 한 절대 움직이지 않으므로), 최종적으로 전진 로직을 제거한 순수 고정-시계 버전으로 커밋했다:

## 3. Baseline-attribution (baseline 귀속)

- 커맨드: 위 각 블록에 명시된 정확한 커맨드.
- 관측 시점/트리: `.claude/worktrees/t33`(브랜치 `WT-auth-ratelimit-flake`), 이 세션에서 직접 실행·관측 — 과거 실행의 수치를 재사용하지 않았다.
- t20 보고서의 "AC-AUTH-021이 두 번 다 실패했다"는 관측(§5)은 t20 세션이 별도로 관측한 것이며, 이 보고서는 그 사실을 원인 추적의 출발점(왜 별도 카드로 이미 알려져 있었는지)으로만 인용하고, 이 카드의 진단·수정·검증은 전부 이 세션에서 새로 수행했다.

## 4. Gaps (미검증)

- **실제 전체-스위트 부하 하에서의 재현 시도는 하지 않았다** — 이번 진단은 페이크 타이머로 메커니즘을 결정론적으로 증명하는 방식을 택했다(`kanban-dispatch.md` "Never spawn background load" 원칙에 따라 인위적 배경 부하를 만들지 않기 위함). 로컬 환경에서 전체 스위트를 3회 반복해도 원래 버그가 실제로 재현되지는 않았으므로(격리 실행과 마찬가지로 이 머신에서는 60초 창에 항상 충분한 여유가 있었다), 실측 실패 사례를 이 세션에서 직접 관측하지는 못했다 — 메커니즘 증명(§2 첫 블록)이 유일한 직접 증거다.
- CI 환경(다른 CPU 코어 수·부하 패턴)에서의 실제 실패 재현 여부는 검증하지 않았다.
- 같은 파일의 다른 10개 테스트, 그리고 `tests/unit/lib/auth/rate-limit.test.ts`의 기존 페이크 타이머 사용 패턴과의 상호작용은 전체 스위트 3회 연속 통과로 간접 확인했을 뿐, 별도의 격리된 상호작용 테스트는 작성하지 않았다.

## 5. Residual-risk (잔여 위험)

- 이 수정은 진단된 메커니즘(절대 시간창 소진)을 구조적으로 제거한다 — 시계가 고정되어 있으므로 실제 bcrypt 호출이 아무리 느려져도 테스트의 판정 자체는 더 이상 실제 경과 시간에 의존하지 않는다. 다만 이것이 "이 테스트가 다시는 절대 실패하지 않는다"는 증명은 아니다 — 예를 들어 Node/vitest의 페이크 타이머 구현 자체가 마이크로태스크 스케줄링에 예기치 않게 개입하는 극단적 사례가 이론적으로 남아 있으나, 이 세션에서는 관측하지 못했다.
- 근본적으로 더 견고한 대안(예: `comparePassword`를 이 테스트에서만 목킹해 real bcrypt를 아예 제거)도 고려했으나 채택하지 않았다 — 이 테스트는 REQ-AUTH-021이 실제 로그인 라우트 전체 경로(비밀번호 비교 포함)를 통과하는 요청에 대해서도 rate limit이 정확히 동작함을 검증하는 것이 의도이며, bcrypt를 제거하면 그 통합적 성격이 옅어진다고 판단했다 — 시계 고정이 더 최소하고 목적에 부합하는 개입이다.
