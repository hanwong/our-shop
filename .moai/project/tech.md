# tech.md — our-shop

> **⚠️ 안내**: 아래 기술 스택은 아직 확정되지 않은 **추천안(Recommendation)**입니다. 사용자가 "TypeScript/JavaScript"만 확정했고 구체적인 프레임워크는 선택하지 않았으므로, 프로젝트 목표(결제 정합성, 카탈로그 p95 300ms, 개인정보 최소 수집)에 맞춰 합리적인 기본값을 제안합니다. 실제 채택 전 사용자 확인이 필요합니다.

## 언어 및 런타임

- **언어**: TypeScript (사용자 확정)
- **런타임**: Node.js (LTS 버전)
  - 근거: TypeScript/JavaScript 생태계 표준 런타임이며, 대부분의 이커머스 프레임워크·PG SDK가 Node.js를 우선 지원한다.

## 프레임워크 (추천, 미확정)

- **추천: Next.js (App Router) + React**
  - 근거:
    - 서버 컴포넌트/SSR을 통해 상품 카탈로그 페이지의 초기 응답 속도를 개선하기 쉬워 p95 300ms 목표에 유리하다.
    - API Routes(또는 Route Handlers)로 백엔드 로직(카탈로그, 장바구니, 체크아웃)을 같은 저장소에서 구성할 수 있어 1인 개발 생산성이 높다.
    - 반응형/모바일 우선 UI 구현에 널리 쓰이는 생태계(Tailwind CSS 등)와 궁합이 좋다.
    - 이미지 최적화, 코드 스플리팅 등 기본 성능 기능이 내장되어 있어 카탈로그 응답/렌더링 속도 목표 달성에 도움이 된다.
  - 대안: Remix, Nuxt(Vue) 등도 가능하나, TypeScript 생태계에서의 채택률과 이커머스 레퍼런스가 풍부한 Next.js를 1순위로 제안한다.

## 데이터베이스 (추천)

- **추천: PostgreSQL** (관계형 DB)
  - 근거:
    - 주문/결제/재고처럼 정합성이 중요한 데이터는 ACID 트랜잭션을 지원하는 관계형 DB가 적합하다. 특히 "결제 데이터 정합성 최우선" 제약과 직접적으로 부합한다.
    - 상품 카탈로그처럼 읽기 위주의 조회 성능이 중요한 영역은 인덱싱·읽기 복제본(read replica)·캐싱(Redis 등)으로 p95 300ms 목표를 보완할 수 있다.
  - 캐싱 계층(추천, 선택): **Redis** — 카탈로그 조회 캐싱으로 p95 응답 속도 목표 달성을 지원.
  - ORM(추천): **Prisma** — TypeScript 타입 안전성과 마이그레이션 관리에 유리.

## 결제(PG) 연동 방식 (추천)

- **접근 방식**: 서버 사이드에서만 PG 시크릿 키를 다루고, 결제 승인/웹훅 처리는 반드시 서버(API Route/백엔드)에서 수행한다.
- **정합성 확보 전략**:
  1. 주문 생성과 결제 승인을 하나의 트랜잭션 경계로 다루거나, 최소한 **멱등키(idempotency key)** 를 사용해 중복 결제/중복 주문을 방지한다.
  2. PG의 **웹훅(webhook)** 을 신뢰 가능한 최종 상태 소스로 삼고, 클라이언트 응답만으로 결제 완료를 확정하지 않는다.
  3. 결제 상태 변경 이력을 별도 테이블에 감사 로그(append-only)로 남겨, 정합성 검증과 장애 복구를 용이하게 한다.
- **PG사 선택**: 특정 PG사는 이번 문서에서 확정하지 않음 — 국내 서비스라면 토스페이먼츠/KG이니시스 등, 해외向이라면 Stripe 등이 일반적인 후보이며, 실제 선택은 사업 요구사항(정산 방식, 수수료, 지원 결제수단)에 따라 별도 결정이 필요하다.

## 개인정보 최소 수집 원칙 반영

- 게스트 체크아웃 시 결제/배송에 필요한 최소 정보(이름, 연락처, 배송지)만 수집하고, 불필요한 회원 전용 정보는 요구하지 않는다.
- 수집한 개인정보는 목적 외 저장을 피하고, 결제 관련 민감정보(카드번호 등)는 PG사 시스템에 위임하여 자체 서버에 저장하지 않는 것을 원칙으로 한다(PG 토큰화 방식 활용 권장).

## 테스트 도구 (사용자 확정 방향에 따른 추천)

- **추천: Vitest** (또는 Jest)
  - 근거: 사용자가 "Jest/Vitest 계열 자동 테스트"를 검증 방식으로 명시했다. Next.js/Vite 기반 프런트엔드와의 통합이 쉬운 Vitest를 1순위로 제안하되, 팀 선호나 기존 생태계에 따라 Jest도 동등하게 유효한 선택지다.
  - 테스트 범위(제안): 유닛 테스트(도메인 로직), 통합 테스트(체크아웃/PG 연동 mock), 성능 테스트(카탈로그 응답 p95 측정).

## 프런트엔드 스타일링 (추천, 선택)

- **추천: Tailwind CSS** — 모바일 우선 반응형 레이아웃 구현 생산성이 높고 Next.js와의 통합 사례가 많다.

## 개발 환경 요구사항 (추천)

> **⚠️ 안내**: 아래 항목은 프레임워크 확정 전 제안되는 추천 개발 환경입니다. 실제 채택 전 확인이 필요합니다.

- **Node.js 버전**: LTS 최신 버전 고정 권장 (예: Node.js 22.x LTS). 저장소 루트에 `.nvmrc` 또는 `package.json`의 `engines` 필드로 버전을 명시해 팀/CI 간 버전 불일치를 방지한다.
- **패키지 매니저**: **pnpm** 권장 — 모노레포/워크스페이스 전환 유연성과 디스크 효율이 좋다. npm도 대안으로 무방하다.
- **로컬 개발 부트스트랩 절차 (제안)**:
  1. `pnpm install` — 의존성 설치
  2. `cp .env.example .env.local` — 환경변수 파일 생성 후 아래 변수 값 채움
  3. `pnpm dev` — 로컬 개발 서버 실행 (Next.js 채택 시 `next dev`)
- **필요 환경변수 (추천 목록, 실제 값은 비밀로 관리)**:
  - `DATABASE_URL` — PostgreSQL 연결 문자열
  - `REDIS_URL` — 캐싱 계층 연결 문자열 (선택)
  - `PG_API_KEY` / `PG_SECRET_KEY` — PG(결제) 연동 시크릿 키 (서버 전용, 클라이언트에 노출 금지)
  - `PG_WEBHOOK_SECRET` — PG 웹훅 서명 검증용 시크릿
  - `NEXTAUTH_SECRET` 또는 동등한 세션/인증 시크릿 (인증 방식 확정 시)
  - `NODE_ENV` — `development` / `test` / `production` 구분
- 위 변수는 `.env.local`(로컬), 배포 플랫폼의 환경변수 관리 화면(스테이징/프로덕션)에 각각 별도로 등록하고, 절대 저장소에 커밋하지 않는다.

## 빌드 및 배포 구성 (추천, 프레임워크 확정 전 잠정안)

> **⚠️ 안내**: 프레임워크(Next.js 추천안) 확정 전이므로 아래는 잠정 제안이며, 실제 CI/CD 파이프라인 세부 구성은 프레임워크 확정 후 별도로 결정한다.

- **호스팅 대상 (추천)**: **Vercel** — Next.js 추천안과의 통합이 가장 매끄럽고, 프리뷰 배포(PR별 미리보기 URL)를 기본 제공해 리뷰 생산성이 높다. 대안으로 자체 컨테이너 배포(Docker + 임의 클라우드) 가능.
- **CI/CD (추천)**: **GitHub Actions** — 다음 단계로 구성 제안:
  1. `lint` — ESLint/타입체크 실행
  2. `test` — Vitest/Jest 유닛·통합 테스트 실행
  3. `build` — 프로덕션 빌드 검증
  4. `deploy` — main 브랜치 머지 시 자동 배포 (Vercel 연동 시 Vercel이 자체 처리 가능, 자체 호스팅 시 별도 배포 스텝 필요)
- **환경 프로파일 (제안)**: `development`(로컬) / `staging`(PR 프리뷰 또는 별도 스테이징 환경) / `production`(운영) 3단계로 구분하고, 각 프로파일마다 별도의 DB·PG(결제) 자격 증명을 사용해 운영 데이터와 테스트 데이터를 분리한다.
- **결정 보류 사항**: 구체적인 CI/CD YAML 워크플로 정의, 컨테이너화 여부, 무중단 배포 전략은 프레임워크 및 PG사 확정 이후 별도 문서/SPEC에서 구체화한다.
